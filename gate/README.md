# `gate` — 검증 규칙의 단일 구현

계약과 프로파일이 어긋나면 PR 이 막힌다. **CI 와 `registry` 가 기준선만 달리해 같은 코드를 부른다**(ADR 22) —
두 벌로 두면 PR 에서 막힌 것이 런타임에 통과하는 날이 온다.

---

## 검사

| # | 무엇을 막나 |
|---|---|
| 1 · 2 | `buf lint` · `buf breaking` — proto 자체의 규율과 파괴 변경 |
| 3 | 프로파일 JSON Schema + 구조 규칙 넷(스키마가 못 보는 것) |
| 4 | 계약 ↔ 프로파일 교차 참조 — proto 에 없는 스킬·키를 프로파일이 선언하면 실패 |
| 5 | `contracts` 의 프로젝트 내 의존 0 |

| 7 | **기종 분기 금지** — 기종을 몰라야 하는 모듈의 소스에 벤더·모델 문자열 |
| 8 | **소스 변경 없는 기종 추가** — 새 프로파일만 더한 PR 에 소스 변경이 섞이면 실패 |

**7·8 번이 이 프로젝트의 두 주장을 CI 실패 조건으로 바꾼다** — *같은 클라이언트 코드로* 와 *프로파일 한 장으로*.

---

## 음성 하네스

**검사가 실제로 막는지를 검사한다.** `gate/negative/` 의 케이스마다 저장소 트리를 복사하고 오버레이를 씌워
게이트를 돌린다 — 그 케이스에서 **지정한 검사가 실패해야** 통과다.

이것이 있는 이유는 실측이다. ★**게이트가 아무 검사도 안 돌리고 종료코드 0 을 낸 적이 있다.** 그래서 `--require` 로
어느 자원이 반드시 있어야 하는지를 못 박고, 음성 하네스가 *조용한 통과* 자체를 막는다 — 그리고 **그 하네스가 자기가
막겠다고 선언한 조용한 통과를 자기 자신이 밟은 적도 있다.**

---

## 문자열 검사인 이유 (ADR 23)

5·7 번은 AST 가 아니라 문자열 검사다. **우회를 막는 장치가 아니라 실수를 막는 장치**이고, AST 는 우회 방법이 더
많고 유지 비용이 크다. 남는 한계는 §15.6·§15.11·§15.28 에 있다 — 기종 식별자를 계산해 만들면 7 번을 지나가고,
능력 기반 분기(`skills.size > 2`)는 기종 이름을 한 글자도 안 쓴다.

---

## 이 모듈의 경계

**`contracts` 에 라이브러리 의존을 안 건다.** 게이트가 필요한 것은 생성 코드가 아니라 `FileDescriptorSet` **바이트**이고,
그것은 런타임 입력으로 받는다. 2026-09-10 부터 그 바이트를 만드는 것은 `protoc`(Gradle)이고 **런타임 신원과 같은
파일**이며, `:gate:test` 가 그 태스크에 태스크 의존으로 매달린다(§15.111) — 예전에는 손으로 `buf` 를 돌려야 했고
**안 돌리면 낡은 디스크립터가 낡은 코드와 사이좋게 초록이었다.**

`DocumentClaimsTest` 도 여기 있다. 게이트가 이미 저장소의 파일을 읽어 규칙을 집행하는 자리이기 때문이고,
**게이트 검사로는 안 만들었다** — 산문의 숫자 하나로 남의 PR 을 막으면 그 검사는 곧 꺼진다.
