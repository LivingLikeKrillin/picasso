## 1. 이 문서가 정하는 것

출발점은 사용자 요구 하나입니다. 운영 중에 변경점이 생길 때마다 코드를 고치는 것이 아니라, 최종 사용자가 관리 화면 안에서 대응하고 처리할 수 있어야 합니다. 이 저장소는 그 변경을 데이터로 관리하고 검증하는 쪽을 맡습니다. 화면에서 값을 입력할 수 있다는 것만으로 이 요구를 충족하지는 않습니다. 변경을 검증하고 적용할 시점을 정하며, 적용 뒤의 실행과 사건을 해당 변경에 연결할 수 있어야 합니다.

다만 모든 변경이 데이터가 되지는 않습니다. 새 스킬 종류, 새 기종, 새 설비 드라이버, 판정 규칙은 코드 작업으로 남습니다. 화면이 **«이 변경은 코드 작업이다» 를 분명히 알리는 것**도 화면의 기능입니다.

| 정한다 | 정하지 않는다 |
|---|---|
| 무엇을 데이터로 두고 무엇을 코드로 두는가의 기준 | 화면 기술과 시각 디자인 |
| 사용자 역할 구분 | 인증과 권한 구현(PoC 에서 생략) |
| 화면 영역 구성 | 임무 정의의 직렬화 형식 세부 |
| 시운전과 운영 중 변경의 유도 순서 | 현장 시간값의 허용 범위 수치 |
| 막힌 단계의 표시 형식 | |
| PoC 에서 입증할 것 | |

## 2. 자리: 이 저장소와 운영 화면 저장소

운영 화면과 그것을 띄우는 서비스 프로세스는 이 저장소에 두지 않습니다. 자리는 `orchestration.md` §8 의 끝 문단이 정했습니다. 실제 하드웨어를 담는 측은 `picasso` 에도 koshei 에도 두지 않고, 현장 운영 측이 소유하는 별도 배치 저장소에 두며, 그 저장소가 `picasso` 를 라이브러리로 씁니다(2026-10-04 바깥 루프 쪽 결정). 운영 화면은 그 저장소에 섭니다. 작업 이름은 picasso-ops 입니다.

| 이 저장소의 몫 | 운영 화면 저장소의 몫 |
|---|---|
| 정의 데이터의 스키마 | 저장 |
| 검증기. 화면과 실행이 같은 규칙을 쓰도록 라이브러리로 냅니다(ADR 22 와 같은 방식) | 변경 절차 |
| 실행기 | 서비스 호스트, 화면 |

검증기를 라이브러리로 내는 이유는 화면에서 통과한 것이 실행에서 막히는 일을 없애기 위해서입니다. 화면 쪽이 규칙을 따로 들면 저장소의 규칙이 바뀔 때 화면이 뒤처집니다.

지금 `ApprovalHost`·`ScenarioHost`·`BundleWriter` 는 시험 소스에 있으므로 배치 저장소에서 새로 씁니다(`orchestration.md` §8). 미결 §15.176(승인 창구와 실행기가 시험 소스에 있어 배포 가능한 프로세스가 아님)과 §15.203(작업 응답을 나르는 실제 하드웨어 담는 측이 없음)이 그 저장소를 기다립니다. 이 문서는 그 2건을 닫지 않고, 닫힐 자리가 그 저장소라는 것만 적습니다.

저장소 경계는 그대로입니다. 다른 저장소로 넘길 것은 `handoff/` 에만 둡니다.

## 3. 지금 무엇이 데이터이고 무엇이 코드인가

옮길 것을 정하기 전에 현재 자리를 적습니다. 아래 표의 «지금» 칸은 실측이며, 이 문서가 바꾸자는 값이 아닙니다.

| 대상 | 지금 | 자리 |
|---|---|---|
| 어댑터 인스턴스 등록 | 데이터(REST) | `POST /operations/adapter-instances` |
| 기체 등록 | 데이터 | 수동 `POST /operations/robots`, 자동 발견 `POST /ingest/robots` |
| 기체 퇴역·복귀 | 데이터 | `POST`·`DELETE /operations/robots/{robotId}/retirement` |
| 사이트 명칭 기록·대조 | 데이터 | `POST`·`GET /operations/site-names` |
| 소비자 요구 스킬 집합 | 데이터 | `POST /requirements` |
| 진단 열람 | 데이터 | `GET /diag/robots` · `/diag/adapter-instances` · `/diag/bindings` · `/diag/stalled` · `/diag/plans` · `/diag/rejections` 등, `GET /catalog` |
| 임무(논리적 능력) | 코드 | `LogicalCapability` Kotlin 클래스 3개(`PrepareSequencedRack`·`DeliverContainer`·`InspectAsset`). 상위 작업 지시의 `WorkMasterID` 로 찾습니다. 새 임무는 코드와 재배포입니다 |
| 현장 시간값 | 코드 기본값 | `evidenceWindow`(설비 확인 시간창)·`inDoubtGrace`·`stallWindow`. 코드 주석이 «현장별로 설정하는 값이며 여기는 기본값» 이라고 적습니다 |
| 바닥·통로 소유 | 코드 배선 | `FloorOwnership`. 주석: «대장은 현장의 것이고 이 저장소 밖에 산다» |
| 작업 구역 | 코드 배선 | `Workspace` |
| 자동 승인 선언 | 코드 배선 | `Entitlements`. 파일에서 읽는 `FileEntitlements` 는 시험 소스에만 있습니다 |
| 배정 비용·재배정 정책 | 코드 배선 | `AssignmentCost`·`ReassignPolicy`. 주석: «값은 배치가 준다» |
| 설비 신호·AMR 플릿 연결 | 코드(포트 구현) | `CellSignals`·`AmrFleetPort` |

«코드 배선» 으로 적힌 것은 전부 `Middleware` 생성자 인자입니다. 레지스트리(`registry` 서비스)는 이미 REST 가 있고, 미들웨어 자체의 HTTP 표면은 시험 소스(승인 창구 호스트)에만 있습니다. 그래서 표의 위쪽은 화면이 오늘 붙을 수 있는 자리이고, 아래쪽은 화면이 붙기 전에 자리부터 만들어야 하는 곳입니다.

이 구분은 새것이 아닙니다. `commissioning.md` §1 은 이미 마스터 데이터(계약 SemVer, 스킬 카탈로그, 어댑터 빌드, 기종 프로파일, 설비 신호 포트 매핑, 시간창, 환경 전제)와 런타임 데이터를 나누고, 관리 주체를 «현장 인프라 및 시스템 설계 엔지니어» 와 «현장 운영자 및 로봇 어댑터 에이전트» 로 나눕니다. 코드 주석이 «여기는 기본값» «값은 배치가 준다» 고 적어 둔 것도 같은 방향입니다. 이 문서는 그 방향에 화면이라는 소비자를 붙입니다.

## 4. 사용자

사용자를 2부류로 나눕니다. 근거는 `commissioning.md` §1 의 관리 주체 칸입니다.

| 부류 | 하는 일 |
|---|---|
| 시운전·통합 엔지니어 | 자원 대장 편집, 신호 사양 작성, 임무 판 작성·모의·활성화, 자격·가중치 선언, 시간값 설정 |
| 운영자 | 실행 감시, 사건 승인과 재작업 판단(ADR 47, 사람의 판단), 퇴역·복귀, 엔지니어가 정한 범위 안의 기한 조정 |

어댑터·플랫폼 개발자는 화면 밖입니다.

**앱은 하나입니다.** 같은 화면을 권한과 모드로 가르고 첫 화면만 다르게 둡니다. 엔지니어의 첫 화면은 준비도·호환성·검증 실패·변경 초안이고, 운영자의 첫 화면은 진행 작업·막힌 이유·조치 요청입니다. 앱을 하나로 두는 이유는 2가지입니다. 작은 현장은 한 사람이 2가지 역할을 모두 맡고, 사건을 보다가 임무 판을 고치러 가는 동선이 필요합니다.

운영자 승인은 명부 없이 성립해야 합니다. ADR 43 은 사람에게 선언을 요구하지 않는다고 정했습니다. 사람까지 대조하면 선언 목록이 운영자 명부가 되고, 명부에서 한 명이 빠진 날 라인이 섭니다. 명부는 엔지니어의 변경 활성화 권한에만 겁니다.

사건 승인과 변경 승인은 종류가 다릅니다. 사건 승인은 제안 하나를 가리키고(ADR 44), 변경 승인은 판을 활성화하는 일입니다. 2가지를 한 버튼으로 합치지 않습니다.

PoC 에서 인증을 생략하더라도 행위자·사유·판 기록은 남깁니다.

## 5. 코드에서 데이터로 옮기는 기준과 대상

옮길지 말지는 4개 기준으로 판정합니다.

| | 기준 | 출처 |
|---|---|---|
| ① | 현장마다 다르고 릴리스보다 빨리 바뀌는가 | ADR 41 의 기준 |
| ② | 틀려도 값만 바뀌고 판정 규칙은 그대로인가 | `commissioning.md` §1 의 파급도 |
| ③ | 라이브러리가 검증 규칙을 들어 화면과 실행이 같은 규칙으로 막을 수 있는가 | §2 의 검증기 |
| ④ | 소유자가 현장인가 이 저장소인가 | `orchestration.md` §2 |

아래 표가 이 기준으로 가른 결과입니다.

| 데이터로 | 코드로 남김 |
|---|---|
| 임무 정의(§6) | 관문(`admits`·`occupancyViolation`·`scopeRefusal`) |
| 현장 시간값(§11 의 결정 2 에 따라 엔지니어 권한으로만 변경) | 실행 진행 규칙(`pump`) |
| `FloorOwnership`·`Workspace` | `IN_DOUBT`·근거 등급·시간창 대조 규칙 |
| `Entitlements`(편집 화면) | 포트 구현체(로봇·플릿·설비 드라이버) |
| `AssignmentCost`·`ReassignPolicy`(엔지니어 권한) | 계약 |
| 설비 신호 사양과 «어느 주소가 어느 신호인가» 의 매핑 | |

주의할 자리가 2곳 있습니다.

- **자원의 소유 규칙과 실행 중의 현재 점유 상태는 다릅니다.** 앞의 것은 데이터이고 뒤의 것은 실행기가 쥐는 상태입니다. 뒤의 것을 설정 편집으로 덮어쓰지 않습니다. 생성자 값을 저장소로 옮기는 것만으로 운영 가능성이 생기지는 않습니다. 옮긴 값이 언제 적용되는지(§6 의 tick 경계)와 잘못된 값을 어디서 막는지(§8 의 활성화 관문)까지 있어야 합니다.
- **사용자가 고르는 것은 기한 값과 기한이 지났을 때 갈 곳까지입니다.** 결과 판정을 바꾸는 값(`evidenceWindow`·`inDoubtGrace`)은 사용자 대기 기한과 다른 칸에 둡니다. 안전 인터록은 열지 않습니다. ADR 32 대로 안전 신호는 전이 조건으로 쓰지 못하게 검증기가 막습니다. 이 저장소의 보증 규칙(`IN_DOUBT`, 설비 확인 시간창, 운영자 판단)은 끌 수 없습니다.

## 6. 임무 정의의 두 층

최종 사용자는 캔버스에 노드와 선으로 임무를 그립니다. Node-RED 같은 노드·선 방식은 화면 방식의 예이며 실행 모델이 아닙니다. 단계와 전이 조건이라는 모양은 PLC 의 SFC(IEC 61131-3)에서 빌립니다(ADR 36).

**두 층으로 시작합니다.** 사용자가 그리는 노드는 2종류입니다.

| 노드 | 담는 것 |
|---|---|
| 단위 | 로봇 스킬 호출 또는 플릿 운반 |
| 설비 대기 | 신호 값, 기한, 기한 뒤 갈 상태 |

단위 하나의 생애와 보증 전이는 엔진이 고정합니다. 지금 단위 상태는 `PENDING`·`RUNNING`·`VERIFYING`·`IN_DOUBT`·`OPERATOR_HOLD`·`DONE`·`UNVERIFIED`·`FAILED`·`ABORTED` 의 9개이며, 사용자는 이 안쪽을 그리지 않습니다.

층을 가르는 이유는 규범의 자리 때문입니다. 사용자가 그린 전이와 엔진이 가진 전이가 같은 층에 있으면 어느 쪽이 규범인지가 문제가 됩니다. 지금 `LogicalCapability.plan()` 은 작업 지시를 실행 단위의 직렬 목록으로 바꾸고, 3개 시나리오 모두 직선입니다. 분기·병렬이 필요한지는 실물 현장이 없어 확인되지 않았습니다. §11 의 결정 1 에 따라 두 층으로 시작하고, 분기와 병렬은 실제로 쓰는 쪽이 생길 때 이 절의 5가지 의미를 먼저 정한 뒤 엽니다.

분기·병렬을 여는 날에는 5가지 의미를 먼저 정해야 합니다. 동시 전이의 우선순위, 반복 횟수, 자원 획득과 반납, 취소와 재시작, 재시도 때 부작용 중복입니다. 이 의미가 없는 분기는 그리는 사람마다 뜻이 달라집니다.

그리는 순간 라이브러리의 규칙으로 검증합니다.

| 검사 | 묻는 것 |
|---|---|
| 기한 | 대기마다 기한과 기한 뒤 상태가 있는가 |
| 신호 | 참조한 신호가 현장 신호 사양에 있는가 |
| 자원 | 쓰는 자원에 소유자가 있는가 |
| 스킬 | 그 단계를 맡을 로봇이 그 스킬을 가졌는가 |
| 안전 | 안전 신호를 전이 조건으로 쓰지 않았는가 |

임무 정의는 판으로 관리하고, 비교할 수 있게 텍스트(JSON)로 저장합니다. 모의 실행을 시험으로 저장해 판을 올릴 때 다시 돌립니다. **실행이 임무 판 번호를 들어야** 도는 실행이 옛 판으로 끝날 수 있습니다. 지금 실행(`Execution`)은 능력 객체(`capability`)를 쥐고 단위는 주문의 `revision` 을 알지만, 임무 정의의 판 번호는 없습니다. 주문의 판을 아는 것만으로는 어떤 임무 정의로 실행했는지 설명할 수 없습니다. 이것은 이 저장소 쪽 변경이며 §11 의 변경 후보에 올립니다.

설정 변경은 실행 진행의 단위 경계(tick)에서 적용합니다. ADR 41 의 단일 적용자 규칙과 같은 자리입니다.

경계를 하나 적어 둡니다. ISA-95 에서 작업 정의(WorkMaster)는 MES 의 것입니다. 이 저장소의 임무 정의는 «MES 가 정의한 작업 하나를 현장에서 로봇·PLC·문을 엮어 어떻게 수행하는가» 입니다(ADR 38 의 조합). 화면이 MES 의 작업 정의를 대신 만들지 않습니다.

## 7. 화면 구성

메뉴는 관리 대상별 5영역으로 두고, 생애주기는 그 위의 유도 흐름 2개로 둡니다. 메뉴를 생애주기 순서로 짜면 처음에는 따라가기 쉽지만, 운영 중에는 대상을 찾아 들어가는 일이 많아 불편합니다.

| 영역 | 담는 것 |
|---|---|
| 현장·자원 | 구역, 자리, 소유자, 설비 신호 사양과 관측 상태, 사이트 명칭 |
| 로봇·연결 | 어댑터 인스턴스, 발견·등록, 바인딩 근거, 스킬 호환성, 퇴역·복귀 |
| 임무·정책 | 상태 모델 편집, `WorkMasterID` 연결, 모의 실행, 배정 설정, 자격 선언, 판 비교·승인·활성화 |
| 운영 | 실행 중 임무를 정의 그림 위에, 대기 대상과 기한, 운영자 판단 대기, 사건과 조치 승인, 작업 응답 |
| 이력 | 판 전환, 선언 변경, 승인, 퇴역·복귀. 삭제 없음 |

유도 흐름 2개는 시운전 체크리스트(Day-1)와 변경 마법사(Day-2)입니다. 순서는 §8 에 있습니다.

**화면 밖에 남는 작업을 화면이 명시합니다.** 로봇 내부 지도와 웨이포인트 티칭(`commissioning.md` §2 Step 3, ADR 35), PLC 프로그래밍, 안전 검증, 어댑터와 설비 드라이버 개발, 계약 SemVer(빌드 설정)가 그것입니다. 화면은 이 작업들의 담당, 요구 사양, 완료 증거, 유효 판만 관리합니다. «완료» 체크 하나로 실제 준비 상태를 대신하지 않습니다.

## 8. 유도 순서

### 8.1 Day-1: 시운전 체크리스트

`commissioning.md` §2 의 10단계(Step 0~9)를 뼈대로 씁니다. 그 문서는 «선행 단계가 완료되지 않으면 후속 단계는 명시적으로 실패한다» 고 적습니다. 화면은 이것을 편집 차단으로 옮기지 않습니다. 시운전은 병렬이기 때문입니다. 티칭하는 동안 신호 사양을 씁니다. **초안은 언제나 쓸 수 있고, 활성화(판 승격)에서만 강한 관문을 겁니다.** 그 관문은 화면만이 아니라 서버에도 있습니다. `Middleware.admits` 가 작업 수락 시점에 거절하는 것과 같은 자리입니다.

권장 흐름은 다음 순서입니다.

1. 자원과 소유자
2. 신호 사양
3. 어댑터와 로봇 등록, 사이트 명칭 대조
4. 임무 초안
5. 모의 실행
6. 활성화(신호, 소유자, 스킬 보유를 전부 대조)
7. 요구 집합 등록
8. 가동

이 순서는 확인하고 활성화하는 순서이며, 작업 시작을 막는 목록이 아닙니다.

단계 카드마다 4칸을 둡니다.

| 칸 | 내용 |
|---|---|
| 무엇이 빠졌는가 | 식별자 |
| 누가 채우는가 | 화면 안인가 밖인가 |
| 근거 | 어느 진단 조회인가 |
| 다음 행동 | 하나 |

단계의 완료는 사용자 체크가 아니라 진단 조회 결과로 판정합니다. 예를 들어 시운전 완료는 `GET /diag/robots` 에서 모든 기체가 `CONFIRMED` 로 바뀐 것으로 확인합니다(`commissioning.md` §2). 등록, 연결, 바인딩, 시운전 완료, 배정 가능은 서로 다른 상태이며 화면도 다르게 표시합니다.

### 8.2 Day-2: 변경 마법사

순서가 거꾸로입니다. Day-1 은 대상에서 출발해 가동으로 가지만, Day-2 는 바꾸려는 의도에서 출발해 영향 범위를 먼저 봅니다.

1. 변경 의도(값 변경, 임무 판, 자원, 기체)
2. 영향 범위(이 신호를 참조하는 임무 판, 도는 실행, 인수 증거)
3. 초안
4. 모의 실행
5. 승인
6. 전환 시점 선택(도는 실행은 옛 판, 새 수락부터 새 판)
7. 관찰

이름 변경과 신호 의미 변경은 재검증 범위가 다릅니다. 선행 설정이 바뀌면 그 뒤의 인수 상태를 미검증으로 되돌립니다.

### 8.3 퇴역

지금 퇴역은 도는 작업을 즉시 끊지 않습니다(§15.123). 그래서 퇴역 전에 그 기체의 도는 실행을 먼저 보여 줍니다. 퇴역이 도는 작업의 자동 취소라는 뜻이 되면 안 됩니다.

### 8.4 막힌 단계의 표시

사유 문장만이 아니라 «종류 + 후속 행동» 으로 보입니다. `orchestration.md` §7.3 의 거부 열거와 같은 모양입니다. 사유 텍스트만 주면 읽는 쪽이 문자열 대조에 기대므로 종류를 열거형으로 두고, 종류를 가르는 기준은 후속 조치입니다.

| 칸 | 내용 |
|---|---|
| 부족한 조건 | 어느 검사가 막았는가 |
| 관측값과 기대값 | 지금 값과 통과에 필요한 값 |
| 마지막 확인 시각 | 그 관측이 언제 것인가 |
| 근거 판 | 어느 판의 설정으로 판정했는가 |
| 해결 담당 | 화면 안의 누구인가, 화면 밖인가 |
| 바로 갈 작업 | 다음 행동 하나 |

## 9. 검증이 잡지 못하는 것

정적 검증과 모의 실행이 통과해도 현장 사실을 보증하지 않습니다. `environment-preconditions.md` §1 은 인프라 보증 전제가 로봇이 관측할 수 없어 영구히 CLAIMED 이며, 관측과 사람의 보증이 분리되지 않으면 대시보드는 정상인데 현장 작업이 실패할 수 있다고 적습니다.

같은 성격의 자리가 더 있습니다.

- 사이트 명칭은 등록 개수만 대조하고 오타를 잡지 못합니다(§15.129).
- 현장 PLC 가 신호 사양대로 설정됐는지는 시운전 신호 대조 전까지 주장입니다.

그래서 화면은 **«관측됨» 과 «사람이 보증함» 을 다르게 표시**하고, 사람이 보증한 것에는 서명자와 날짜를 남깁니다. 신호는 값만이 아니라 품질(응답 없음, 단절, 불확실)도 보입니다.

설정을 되돌려도 이미 움직인 로봇과 설비는 되돌아가지 않습니다.

잘못된 값의 파급은 값마다 다릅니다. `evidenceWindow` 의 앞쪽 폭을 늘리면 옛 신호가 완료 근거로 들어오고, 뒤쪽 폭이나 `inDoubtGrace` 를 줄이면 `UNVERIFIED` 와 운영자 대기가 늘어납니다. 범위는 라이브러리가 쥐고 화면은 범위 밖 값을 막습니다. 어느 판의 설정에서 난 사건인지 되짚을 수 있도록 사건 기록에 판 번호를 싣습니다.

## 10. PoC 에서 입증할 것

| # | 입증 | 비고 |
|---|---|---|
| 1 | 로봇 생애주기 한 바퀴를 화면에서: 등록, 시운전 확인(진단 조회 근거), 가동, 퇴역, 복귀 | `registry` 가 이미 있어 가장 쌉니다 |
| 2 | 현장 값 한 벌을 화면에서 바꾸면 다음 tick 부터 적용되고, 사건 기록에 그 값과 판 번호가 실린다 | §6 의 tick 적용과 §9 의 판 번호 기록 |
| 3 | 임무 하나(`PrepareSequencedRack`)를 데이터 판으로: 모의 실행(mimic) → 활성화 → 도는 실행 중 새 판 전환 → 옛 실행은 옛 판으로 끝난다 | **이것이 핵심입니다.** §6 의 «실행이 판 번호를 든다» 가 없으면 성립하지 않습니다 |
| 4 | 잘못된 변경 하나(신호 사양에 없는 신호 참조)가 활성화에서 거절된다 | 결함 주입으로 확인합니다. 거절이 부족한 조건과 후속 행동으로 표시되는지도 봅니다(§8.4) |
| 5 | 지연, 단절, 묵은 값, 재시작을 넣으면 사건과 사람의 판단으로 이어진다. 재시작 뒤 중복 명령과 중복 결과 통보를 막는다 | |

합격 기준은 3가지입니다. 정해진 현장 변경을 코드 수정 없이 처리하는가, 잘못된 변경은 막는가, 어느 판으로 무엇이 일어났는지 나중에 설명할 수 있는가.

에뮬레이터로는 운영 절차를 입증할 수 있으나 실물 성능, 안전, 벤더 호환성은 입증하지 못합니다.

PoC 밖에 두는 것: 범용 캔버스의 완성도, 보안, 배정 정책 화면, 통로 소유(§15.154, 소유자 미정).
