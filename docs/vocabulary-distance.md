# 어휘 거리 측정 절차 — 이종 벤더 API와 계약 스킬 간 적합성 분석

신규 로봇 기종을 인터페이스 계약에 연동할 때 수행되는 가장 핵심적이고 엄밀성이 요구되는 단계입니다. 이 단계의 판정 오류는 하위의 모든 기계적 자동화 검증을 무력화할 위험이 있습니다. 기계적 검증 파이프라인은 판정 결과의 '논리적 일관성'을 검증할 뿐, 벤더 API에 대한 분석자의 '해석 정확성' 자체를 검증하지 못하기 때문입니다.

본 문서는 분석자의 주관적 자의성을 배제하고 오류 발생 가능성을 최소화하기 위한 표준 분석 절차(SOP)를 규정합니다.

최종 산출물은 `profile/distance/<기종>.json` 파일이며, 스키마 규격은 [`profile/schema/distance.schema.json`](../profile/schema/distance.schema.json)에 정의되어 있고 `gate` 모듈의 `VocabularyDistanceTest` (13개 테스트 케이스)를 통해 기계적으로 엄격히 강제됩니다.

## 1. 9단계 표준 분석 절차

반드시 아래 번호 순서에 따라 단계별로 분석을 진행합니다. 특히 3번(계층 결정)이 4번(파라미터 매핑)보다 선행되어야 합니다.

| 단계 | 분석 작업 내용 | 산출 필드 / 파일 |
|---|---|---|
| 1 | **조사 범위(Survey Scope) 명시**: 분석 대상(서비스 목록, 메시지/IDL 정의, 클라이언트 코드, 공식 예제)의 전수 범위 정의 | `survey_scope` |
| 2 | **공식 벤더 심볼 추출**: `tools/vendor-manifest/`를 사용하여 원문에서 심볼명과 SHA-256 추출 (원문 코드는 커밋하지 않음) | `adapter-*/src/test/resources/vendor-manifest.txt` |
| 3 | **아키텍처 제어 계층 확정**: 당사 태스크 수명주기(수락·일시정지·취소·재시도·작업자 개입)와 대응되는 벤더 제어 계층 판별 | `layer.vendor_layer` |
| 4 | **파라미터 전수 매핑**: 인터페이스 계약의 각 파라미터가 벤더 API 어디에 바인딩되는지 대조 (미확인 시 `NOT_SURVEYED` 유지) | `parameter_map` |
| 5 | **매핑 기반 도달성 판정**: 파라미터 매핑 표를 선행 완성한 후 도달성 최종 판정 | `reachable` · `missing` |
| 6 | **실행 제약 유형 분류**: `YES`로 판정된 항목을 포함하여 제약 유형 태깅 | `limitations` |
| 6b | **스킬 실행 범위(Scope) 설정**: 각 스킬이 구동되는 계층 정의 (문서 레벨 계층은 각 스킬의 최댓값으로 수렴) | `execution_scope` |
| 7 | **어댑터 책임 구현 항목 명세**: 미지원 기능을 메우기 위해 어댑터가 직접 구현해야 할 소프트웨어 요구사항 도출 | `adapter_must_own` |
| 8 | **검토 서명 및 도장 갱신** | `review` |
| 9 | **최종 기종 프로파일 작성**: 상기 분석 완료 후 프로파일 생성 | `profile/profiles/<기종>.json` |

### 순서 결정의 엔지니어링 근거

- **3번(계층 확정)이 선행되는 이유**: 제어 계층 판별 결과가 기종 전체의 지원 특성을 좌우합니다. Unitree G1은 `NONE` 계층(Sport 모드가 단순 모빌리티 명령만 수신)이며, BD Spot은 `MISSION` 계층을 지원합니다. 기종 간 거리는 개별 스킬 차이 이전에 아키텍처 계층 차이에서 기인하므로, 계층이 확정되지 않은 상태에서 개별 스킬을 분석하면 중복 혼선이 발생합니다.
- **5번(도달성 판정)이 4번(매핑) 이후인 이유**: 판정을 먼저 내리면 매핑 표가 판정을 사후 정당화하는 서류로 전락합니다. 매핑 표를 먼저 작성하면 빈칸(`NOT_SURVEYED`)이 남아 있는 한 기계적으로 `YES` 판정을 내릴 수 없도록 검증 파이프라인이 차단합니다.

## 2. 발생 가능한 6대 분석 함정과 방지 대책

| 함정 유형 | 실사례 및 위험성 | 방지 대책 |
|---|---|---|
| **조사 범위 미한정 판정** | Spot의 전체 54개 서비스 중 3개만 조사하고 "특정 기능 부재"로 잘못 결론지어 전수 조사 후 3개 판정이 번복됨 | 1단계 `survey_scope` 명시를 의무화하여 조사 모수 강제 |
| **API 부재와 기능 불가의 혼동** | 고수준 단일 '놓기' 액션이 없다는 이유로 `pick_place` 전체를 불가 판정함 (기존 저작 API 조합으로 합성 가능) | 기본 API 조합 구현(`SYNTHESIZED`)과 근본적 부재(`UNMAPPED`)를 엄격히 분리 |
| **RPC 메서드 부재 시 정보 부재로 속단** | G1에 취소 RPC 메서드는 없었으나, 상태 토픽 `SportModeState_` 내에 `task_id`와 `task_time`이 존재함을 뒤늦게 발견 | 2단계 심볼 추출을 원시 메시지/IDL 정의까지 전수 확장 |
| **판정 유효 표면 미명시** | "진행 중 동작 취소 API 부재"라는 판정이 알고 보니 로코모션 표면에만 국한된 사실이었음 | 판정 기술 시 반드시 대상 서브시스템/표면 명칭을 병기 |
| **어휘 일치와 시맨틱 일치의 혼동** | 계약의 `DELIVERED`는 (도착 ∧ 하역 ∧ 인수 ∧ 미보유)를 의미하나, 벤더의 단순 "도착" 신호와 직결하여 허위 완료 발생 | 계약 상태의 전제 조건을 명제 단위로 분해한 후 벤더 상태와 1:1 대조 |
| **기종 단위 일괄 판정** | Spot은 저수준 명령 표면만으로 `move_relative` 실행이 가능함에도 기종 전체를 묶어 오판단할 위험 | 기능 표면 및 스킬 단위로 세분화하여 `reachable`과 `limitations` 독립 평가 |

## 3. 파라미터 매핑 5대 분류 (`parameter_map[].kind`)

| 매핑 분류 | 정의 | 적용 예시 |
|---|---|---|
| `DIRECT` | 벤더 API 인자에 1:1로 직접 매핑됨 | Digit `location` → `action-goto.reference-frame` |
| `CONVERTED` | 시맨틱은 동일하나 단위·좌표계·표현 형식이 달라 어댑터 변환 필요 | Spot `duration` → `end_time` (상대 시간(초) → 절대 타임스탬프) |
| `SYNTHESIZED` | 벤더에 직접 대응 파라미터가 없어 어댑터가 복수 호출을 조합 생성 | Spot `destination` — 매니퓰레이터 궤적과 그리퍼 동작의 순차 제어 합성 |
| `UNMAPPED` | **대응 불가능 판정.** 1차 벤더 근거 자료가 반드시 뒷받침되어야 함 | — |
| `NOT_SURVEYED` | **분석 미수행 상태.** 아직 검토되지 않은 항목 (기술 부채) | 선택 파라미터 매핑 대기 |

`UNMAPPED`(명확한 부재 판정)와 `NOT_SURVEYED`(조사 미완료)의 엄격한 분리가 핵심입니다. 부재를 단정하려면 공식 문서 상의 근거가 필수적이며, 조사되지 않은 영역을 묵인하지 않고 드러내기 위해 도입되었습니다.

## 4. 실행 제약 7대 분류 (`limitations`)

Open-RMF가 플릿 단위로 `Full Control`, `Traffic Light` 등급을 부여한 것과 달리, **본 아키텍처는 (기종 × 스킬) 단위로 정밀 제약을 부여**합니다.

| 제약 분류 코드 | 기술적 정의 | 대표적 발견 사례 |
|---|---|---|
| `TARGET_NOT_ADDRESSABLE` | 동적 파라미터로 대상을 직접 지정할 수 없음 | Orbit `navigate_to` (사전 저작된 미션 지점만 접근 가능) |
| `POSITION_NOT_IDENTITY` | 대상의 고유 신원이 아닌 단순 공간 좌표로 지시 | Spot `pick_place` (이름-좌표 바인딩이 질의 시점에 고정) |
| `NO_TERMINAL_SIGNAL` | 하드웨어에서 작업 완료 신호를 명시적으로 주지 않음 | G1 `move_relative` (어댑터가 내부 타이머로 완료 추정) |
| `NO_CANCEL_OR_PAUSE` | 실행 중인 동작을 중단하거나 일시정지할 수단 부재 | G1 로코모션, Orbit 미션 실행 |
| `NO_PROGRESS` | 동작 진행률을 정량적으로 산출할 피드백 채널 부재 | G1, Orbit |
| `NO_RESULT_CHANNEL` | 작업 실행 상세 결과를 반환할 데이터 채널 부재 | Digit `inspect` (현재 스킬 미지원 상태이므로 미사용) |
| `MULTI_STEP_COMPOSITION` | 단일 원자적 액션이 아니며 복수 절차의 시퀀스 합성 필요 | Digit `pick_place`, Spot 하역 동작 |

`YES`로 판정된 도달 가능 스킬이라도 위 제약 분류가 부착될 수 있으며, 이는 어댑터 계층이 흡수하고 보완해야 할 엔지니어링 구현 책임(`adapter_must_own`)을 직접 지시합니다.

## 5. 자동화 분석 도구 활용 시 초안 작성 규칙

대량의 API 명세를 전수 분석할 때 기계적 추출 도구를 활용할 수 있으나, 인간의 비판적 검토를 보장하기 위해 다음과 같은 제약 규칙이 강제됩니다.

**기계 생성 초안은 반드시 `evidence_grade: "MACHINE_DRAFT"`로 명시**해야 합니다. 해당 등급이 부여된 항목은 `reachable` 값이 반드시 `UNKNOWN`이어야 하며, 이는 JSON 스키마와 테스트 코드 양쪽에서 엄격히 강제됩니다.

| 기계 초안 자동 생성 허용 항목 | 기계 초안 자동 생성 금지 항목 (인간 분석 필수) |
|---|---|
| `survey_scope` (조사 대상 및 심볼 모수 집계) | `reachable` (도달 가능성 최종 판정) |
| `parameter_map` 후보 추천 및 원문 인용 | `missing` (부재 확정 판정) |
| `vendor_primitive` 후보 식별 | `adapter_must_own` (어댑터 구현 스펙 견적) |
| — | `layer.vendor_layer` (아키텍처 제어 계층 결정) |

### AI 환각 방지 메커니즘

기계 초안이 가상의 API 심볼(`bosdyn.api.GraspService` 등)을 인용할 경우, "인용된 심볼이 공식 매니페스트에 존재해야 한다"는 게이트 검증에 의해 커밋 단계에서 차단됩니다. 따라서 공식 매니페스트 추출(2단계)이 모든 자동화 분석의 필수 전제 조건입니다.

## 6. 기계적 자동화 검증의 유효 범위와 한계

### `VocabularyDistanceTest`가 보증하는 항목 (기계적 일관성)

1. 계약에 정의된 모든 스킬이 기종별로 누락 없이 측정되었는지 여부
2. 도달 가능(`YES`) 판정 항목과 프로파일의 선언 스킬 일치 여부
3. 프로파일이 선언한 스킬을 해당 기종 어댑터가 실제 지원하는지 여부
4. 문서에 기재된 계층이 개별 스킬들의 최대 계층과 일치하는지 여부
5. 도달 가능 스킬의 파라미터 매핑 누락(`NOT_SURVEYED`) 존재 여부
6. 필수 파라미터 미검토 상태에서의 `YES` 판정 차단
7. 인용된 모든 벤더 심볼의 매니페스트 실재 여부
8. 기계 초안(`MACHINE_DRAFT`)의 임의 판정값 기재 차단
9. 부재(`UNMAPPED`) 판정 시 1차 근거 기재 여부

### 기계적 검증이 보증하지 못하는 항목 (의미적 정확성)

자동화 검사는 **분석자가 내린 해석 판정의 사실 여부 자체**를 검증할 수는 없습니다. "도달 가능하다고 기재했으나 실제로는 동작하지 않는" 오판단은 실물 기체 또는 정밀 HIL 시뮬레이터 연동 검증(C-3)을 통해서만 최종 확인될 수 있습니다.

## 7. 타 표준 프레임워크와의 비교

| 프레임워크 | 등급 분류 단위 | 분석 근거의 시스템 내 영속성 |
|---|---|---|
| **Open-RMF** | 기종(플릿) 단위 (`Full Control`, `Traffic Light`) | 코드 및 설정 파일에 흡수되어 원본 분석 근거 유실 |
| **openTCS** | 주문별 `canProcess` 동적 불리언 평가 | 분석 근거가 구현 내부에 은닉됨 |
| **VDA 5050** | AGV의 `factsheet.agvActions[]` 정적 선언 | 선언 스펙만 유지되며 매핑 근거 부재 |
| **picasso** | **(기종 × 스킬) 매트릭스 단위** | `evidence`, `survey_scope`, `missing`, `adapter_must_own` 데이터로 영구 보존 |

### VDA 5050 `actionScopes` 개념의 차용 및 재해석

VDA 5050의 `node` / `edge` 스코프는 그래프 기반 경로 계획에 종속된 개념이므로, 태스크 큐 방식을 취하는 본 시스템에 직결하기 어렵습니다. 따라서 "해당 액션이 어느 계층에서 실행되는가"라는 본질적 질문만을 수용하여 시스템 고유의 `execution_scope` 메타데이터로 재구성하였습니다.

실제로 `SpotAdapter`는 내부적으로 `Layer { COMMAND, MISSION, ACQUISITION }`를 보유하고 태스크별 실행 계층에 따라 완료 폴링, 취소, 업데이트 전략을 분기 처리합니다.

본 절차는 [`tools/adapter-template/`](../tools/adapter-template/README.md)의 기반 입력으로 활용되며, 1~8단계의 어휘 거리 측정이 선행 완료되어야 9단계 어댑터 구현 및 기체 프로파일 생성이 가능합니다.
