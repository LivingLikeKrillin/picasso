# 한계 대장 — 무엇이 열려 있고, 무엇이 있어야 닫히나

2026-09-10 정리. 설계 문서의 **§15 는 대장이 아니라 일지**다 — 번호가 106 까지 갔고 앞쪽(1~45)은 한계 목록,
뒤쪽은 무엇을 지었고 무엇이 드러났는지의 기록이다. 그래서 *"지금 무엇이 열려 있나"* 를 물으면 일지를 처음부터
읽어야 했다. 이 문서가 그 답을 한 장으로 준다.

**읽는 법.** 닫힌 것은 여기 없다 — §15 의 해당 항목이 `(닫힘)` 또는 취소선으로 표시한다. 여기 있는 것은
**지금도 참인 한계**이며, 세 갈래로 나뉜다.

| 갈래 | 뜻 |
|---|---|
| **의도적 밖** | 범위 결정이라 닫지 않는다. 닫으려면 결정을 뒤집어야 한다 |
| **열림 — 안에서 닫는다** | 이 저장소가 지으면 닫힌다. 무엇을 지으면 되는지가 적혀 있다 |
| **열림 — 밖에서 닫는다** | 실물·조직·상류가 있어야 닫힌다. 지어서 닫을 수 없다 |

---

## 1. 의도적 밖 — 닫지 않기로 한 것

| 출처 | 무엇 | 왜 닫지 않나 |
|---|---|---|
| §1.3 B-1 | 무선 단절 대응의 **집행**(재접속 정책·페일세이프) | 비목표. 계약은 단절을 **보이게** 하고 대응은 배치가 정한다 |
| ADR 32 · 시나리오 5 | 안전 기능(비상정지·보호정지·즉시 kill) | 이 계약이 나르지 않는다. 안전은 자체 계통이며 소프트웨어 계약 위에 얹으면 **얹은 만큼 안전해 보인다** |
| §15.3 | 감사 로그가 부인방지 근거가 아니다 | 행위자 신원을 요청 헤더에서 받는다. 조사 단서로만 쓴다 |
| §15.5 | 런타임 갱신의 폴링 지연 5 초 | push 로 줄이면 `registry → mimic` 간선이 생겨 §3.2 가 깨진다 |
| §15.6 · §15.11 · §15.28 | 게이트 5·7 번이 문자열 검사다 | ADR 23. AST 는 우회 방법이 더 많고 유지 비용이 크다. **실수를 막는 장치이지 우회를 막는 장치가 아니다** |
| §15.9 | 다중 사이트가 스키마·토픽·카탈로그에만 있다 | 사이트별 배포 격리와 브리지 정책은 비목표 |
| §15.33 | 제어 채널이 인증하지 않는다 | `mimic` 은 시험 도구다. 루프백 바인딩이 방어의 전부 |
| §15.37 | 거절 표에만 `robot_id` FK 가 없다 | 등록되지 않은 기체에 날아온 거절도 운영자가 알아야 한다. 대가는 오타가 조용히 적재되는 것 |
| §15.87 | 점검 결과를 실을 자리가 `partial_result` 뿐이다 | 결과의 모양은 상류가 정한다. 계약이 스키마를 가지면 그 순간 상류를 하나로 못박는다 |

## 2. 열림 — 이 저장소가 지으면 닫힌다

가장 값이 큰 것부터 적는다.

> **셋이 닫혔다 (2026-09-10).** `buf` 디스크립터(§15.111) · 계약의 `progress` 에 *못 잰다* 자리(§15.112) · **멈춘 태스크의 갱신**(§15.113 — 포트를 한 칸 넓혔더니 §4.4 의 표가 다 찼다).
>
> **앞의 둘이 닫힌 방식:** `buf` 디스크립터(§15.111)와 **계약의 `progress` 에 *못 잰다* 자리**(§15.112 — 닫는 조건이던 *정체로 개입을 판단하는 소비자* 를 함께 지었다).
>
> **`buf` 디스크립터는**(2026-09-10, §15.111). ★적어 둔 대가(`:gate:test` 에 Docker 가 번진다)를 **안 치렀다** — 디스크립터가 둘이라는 것이 문제의 절반이었고, protoc 이 이미 만들던 것으로 합치니 Docker 가 늘지 않았다. **닫는 조건을 적어 두면 그것을 다시 읽을 때 더 나은 길이 보인다**는 것이 이 대장의 첫 수확이다.

| 출처 | 무엇 | 무엇이 있어야 닫히나 |
|---|---|---|
| §15.34 | **관측 적재에 구독기가 없다.** 발행은 `MqttPublisher` 로 실제 브로커까지 가지만, 그것을 **읽어** 원장에 넣는 것은 아무도 아니다 — 지금 적재는 발신자가 `IngestBridge` 로 직접 민다 | 브로커 구독기가 `ObservationService.recordHeader`/`recordRejection` 을 부르면. 입력이 `MessageHeader` 인 것이 그 경계를 이미 열어 뒀다 |
| §15.8 | 재생 버퍼가 프로세스 메모리에 있다 | 지속 저장소. 지금은 **못 보낸 구간을 버리면 세션을 새로 내** 소비자가 결손을 알게 하는 것까지 한다(§15.107) |
| §15.106 | Orbit 배치에 **CLI 가 없고**(인자 파싱·기동 거부 메시지·프로세스 유지) **발견이 기동 때 한 번**이다 | 짓기만 하면 된다. 미믹의 `MimicCli` 가 그 모양을 이미 보여 준다 |
| §15.106 | 발견된 기체 **전부에 프로파일 하나**를 적용한다 | 플릿이 기종을 말해 주면. `Robot` 자원에 기종 칸이 없어 **지금은 알아낼 방법이 없다** — 이것만 밖이다 |
| §15.19 | `mimic` 이 게이트가 거절할 프로파일로 기동할 수 있다 | 기동 경로가 검사 3번의 구조 규칙 넷을 함께 부르면 |
| §15.123 | **퇴역이 로봇을 멈추지 않는다.** 원장의 목록에서 내리는 것이고, 그 기체의 바인딩과 진행 중인 작업은 그대로다 | 퇴역이 바인딩을 함께 내리면. **지금 안 하는 이유는 그것이 다른 질문이기 때문이다** — 목록에서 빼는 것과 일을 못 시키게 하는 것은 같은 버튼이 아니다 |
| §15.13 | proto 하나가 나쁘면 `ContractIndex` 가 통째로 실패한다 | 실패를 파일 단위로 가두면. 지금은 안전한 방향(빨간불)이라 급하지 않다 |
| §15.18 | 검사 6 의 `optional_fields` 매칭이 접미사 일치다 | 스킬 타입까지 키에 넣으면 |
| §15.20 | protobuf-gradle-plugin 0.9.4 가 **Gradle 10 에서 깨진다** | 플러그인 버전을 올리면. Gradle 10 이전에 해야 한다 |
| §15.21 | `session_id` 가 ULID 가 아니라 기동 카운터다(미믹·호스트 **둘 다**) | ULID 를 쓰되 §12.1 의 결정성을 시드로 따로 관리하면. 같은 밀리초 재기동에서 세션이 겹칠 수 있는 것이 대가 |
| §15.23 | `MAJOR_MISMATCH` 가 minor 부족까지 덮는다 | 계약에 코드 하나. **발신자와 소비자가 둘 다 있으므로**(협상) ADR 9 는 통과하며, 안 한 이유는 §12.2 의 다섯 고정뿐이다 |
| §15.24 | `GetCapabilitiesResponse` 에 `Rejection` 자리가 없다 | 계약에 자리 하나. 그 RPC 만 gRPC 상태로 나가는 유일한 예외가 사라진다 |
| §15.25 | `update_index`·`sequence` 가 0 부터라 헤더에서 미설정과 구별되지 않는다 | 계약 major. `schema_id` 가 방향을 말하므로 실질 문제는 없다 |
| §15.26 | 일시정지 중에도 미믹의 진행률이 흐른다 | 미믹이 멈춘 시간을 빼면. 계약 위반은 아니다(구간 안 단조 비감소만 요구) |
| §15.31 | 이벤트를 접는 소비자가 §4.5 표에 없는 조합을 잠시 볼 수 있다 | 두 사실을 원자적으로 발행할 수단. 없으면 *정착한 상태만 표의 대상* 이라는 지금 규칙이 답이다 |
| §15.32 | 제어 채널 proto 가 `buf lint`·`breaking` 밖이다 | 두 번째 buf 모듈. Docker 호출이 하나 는다 |
| §15.36 | 세대 이력의 접기가 사유를 키에 넣어 되풀이 횟수가 사라진다 | 카운터 열 하나 |
| §15.41 | 관측선 신선도 창이 24 시간 상수이고 판정이 기체 단위다 | 사이트별·스트림별 설정 |
| §15.14 | 게이트 6 번이 허용값·길이·범위 **축소**를 경고로만 낸다 | §5.2 가 그 셋을 파괴로 분류하면 오류로 올린다 |
| §15.98 | 호스트가 태스크를 한 번에 하나만 든다 | 어댑터 넷이 모두 배타 제어라 지금은 맞다. 여럿을 드는 기종이 나오면 |

## 3. 열림 — 밖에서만 닫힌다

| 출처 | 무엇 | 무엇이 있어야 닫히나 |
|---|---|---|
| **C-3** | **어댑터 넷 중 어느 것도 실물에 붙여 보지 못했다** | 실물 또는 벤더의 실기 동급 시뮬레이터. 이 프로젝트의 전제이며 **다른 모든 벤더 판정의 상한**이다 |
| §15.1 | 벤더가 선언을 그대로 두고 거동만 바꾸면 게이트가 못 본다 | 적합성 역검증(C-3). 그때까지의 방어는 *프로파일을 벤더 문서에서 파생시키고 괴리가 보이면 고친다* 하나 |
| §15.2 | 프로파일이 **형상별 파지 가능성**을 못 담는다 | 어디까지가 선언이고 어디부터가 해 봐야 아는 것인지의 결정. Digit 의 `object-attribute.pickable` 처럼 **답을 가진 벤더가 있다**(§15.81) |
| §15.10 | 원장은 모두가 이 계약을 지날 때만 정확하다 | 조직적 합의. **기술로 강제되지 않는다** |
| §15.81 | 능력은 (기체 × 현장)의 성질인데 **현장이 보증하는 것**이 계약 어디에도 없다 | 현장을 말하는 발신자. `docs/environment-preconditions.md` 가 그 입력을 모아 두었다 |
| 시나리오 §8 | 층 ② 의 어휘(논리적 능력의 이름) | 실제 상류. ADR 36 이 *상류나 벤더가 이미 가진 것만 들인다* 고 정했다 |
| §15.15 · §15.16 · §15.29 · §15.39 | CI 에서만 도는 검사들(Docker·PR 기준선·`git diff` 상태 문자) | 환경의 성질이다. **건너뛴 것이 초록으로 보이지 않게** 하는 것까지가 우리 몫이고 그것은 `--require` 로 했다 |

## 4. 이 대장을 어떻게 유지하나

- **닫으면 §15 의 해당 항목에 `(닫힘)` 을 적고 여기서 지운다.** 두 곳에 같은 상태를 적으면 곧 어긋난다.
- **새 한계는 §15 의 일지에 먼저 적힌다.** 일지가 정본이고 이 문서는 색인이다.
- **시퀀스 다이어그램은 자동으로 안 지켜진다**(§15.119). 그림의 내용은 사람이 코드에 대고 훑어야 하며, 마지막 검토는 2026-09-10 이다 — 그때 셋이 틀려 있었다.
- 숫자로 셀 수 있는 진술(모듈 수·검사 수·어댑터 수·진단 수)과 **문서 사이의 링크**는 `DocumentClaimsTest` 가 코드에서 세어 대조한다 — 산문이 낡는 것을 사람이 훑어 막지 않는다.
- **어디까지가 진짜인지**는 [`verification.md`](verification.md) 가 구간마다 적는다. 이 대장이 *무엇이 없나* 라면 그쪽은 *있는 것이 얼마나 진짜인가* 다.
