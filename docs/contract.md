# 인터페이스 계약 명세서 — 계약 보증 규격 및 진입 기준

`picasso/v1`은 본 미들웨어 시스템의 유일한 **공개 인터페이스 면(Public Surface)**입니다. 상위 시스템 소비자는 본 계약 인터페이스만을 참조하며, 하위 로봇 어댑터는 본 인터페이스 규격을 구현합니다.

본 문서는 본 계약에 **어떤 항목이 진입할 수 있는지(진입 기준)**, 그리고 진입한 인터페이스가 **시스템적으로 어떤 성질을 보증하는지(계약 보장 사항)**를 규정합니다.

- 컴포넌트 접합부 명세: [`seams.md`](seams.md)
- ISA-95 상위 표준 데이터 모델 연계: [`isa95.md`](isa95.md)
- 구간별 검증 수준 및 환경 신뢰도: [`verification.md`](verification.md)

## 1. 인터페이스 계약 진입 기준 (2대 관문)

신규 필드, RPC 메서드, 에러 코드가 계약에 추가되기 위해서는 다음 두 가지 기준을 반드시 충족해야 합니다:

### 1.1 관문 1: 소비처 실재 원칙 (ADR 9)
- **실제 소비자가 존재하지 않는 사양은 선언하지 않습니다.**
- 인터페이스 선언이 공개되는 즉시 소비자는 해당 필드의 가용성을 전제하기 시작하므로, 이후 제거 시 호환성 파괴(Breaking Change)가 발생합니다.
- 예: 파지 실패를 거부 코드로 선언하려던 시도는 벤더가 이를 사전 선언이 아닌 런타임 피드백으로만 통보한다는 점이 확인되어 배제되었습니다 (§15.79).

### 1.2 관문 2: 표준 및 기존 어휘 기반 원칙 (ADR 36)
- **상위 시스템 표준 또는 로봇 벤더 인터페이스 중 최소 한쪽에 이미 존재하는 개념만을 수용합니다.**
- 양쪽 어디에도 존재하지 않는 임의 어휘는 번역(Translation)이 아닌 시스템 창작(Invention)이 되어 현장 적용 시 정합성이 결여됩니다.
- 수명주기(Lifecycle) 및 제어 권한(Lease)은 양측에 공통으로 존재하여 채택되었습니다. 반면, 자체 정의했던 스킬 카탈로그는 양측 모두에 부재하여 실제 하드웨어 정합성 검증을 통과하지 못했습니다 (ADR 36).
- `skill_catalog.proto`는 메이저 버전 하위 호환성 유지를 위해 프로토콜에 잔류하고 있으며, 지금도 스킬 타입 **넷**이 거기 있다 (ADR 36 결정 4). 다만, 신규 인터페이스 설계 시 이러한 계층 혼용을 엄격히 배제합니다.
- 복수 기종이 공통 지원한다고 해서 좋은 계약 요소인 것은 아닙니다. 예컨대 `move_relative`는 보편적으로 지원되나, 배정이 아닌 저수준 모터 실행 계층에 속하므로 상위 계약 요소로 부적합합니다.

## 2. 계약 제외 항목 (Out-of-Scope) 및 분리 근거

| 계약 제외 항목 | 제외 근거 | 책임 계층 및 처리 방식 |
|---|---|---|
| **하드웨어 비상정지·보호정지·사람 감지** | ADR 32 — 안전 기능은 미들웨어 소프트웨어 가용성과 물리적으로 격리되어야 함 | 독립 하드웨어 안전 루프 (Safety PLC) |
| **명령 왕복 지연(RTT) 상한 보증** | ADR 32 — 본 인터페이스 면은 엄격한 실시간성(Hard Real-time)을 보장하지 않음 | 제어 루프 내부 (계약 외 범위) |
| **현장 시설물 제약 (도어 개폐, 조도 등)** | 로봇의 실제 역량은 기체 단독이 아닌 `(기체 × 현장 인프라)`의 결합 속성임 | [`environment-preconditions.md`](environment-preconditions.md) |
| **작업 배차 및 로봇 할당 결정** | ADR 36 계층 ③ | 미들웨어 오케스트레이션 코어 (`picasso`) |
| **벤더 미션 시퀀스 조합 및 제어 정밀도** | ADR 36 계층 ⑤ — 상위 시스템에 대한 내부 세부사항 은닉 | 로봇 어댑터 내부 |
| **시설물 명칭과 로봇 내부 좌표 매핑** | ADR 34·35 — 시맨틱 결속의 책임 주체는 로봇 기체 자체임 | 로봇 내부 (현장 맵 등록 작업) |

> **설계 원칙:** 안전 기능(E-Stop 등)을 소프트웨어 계약 위에 통합할 경우, 버퍼링 및 세션 재연결 메커니즘을 통과하게 되어 치명적인 지연을 초래하므로 원천 분리합니다.

## 3. 계약 보장 사항 및 자동화 검증 매핑

모든 계약 보증 사항은 이를 증명하는 자동화 테스트와 1:1로 결속되어야 합니다. `DocumentClaimsTest`가 본 표의 테스트 클래스 및 메서드 존재 여부를 자동으로 대조 검증합니다.

| 담보 | 무엇을 약속하나 | 지키는 시험 |
|---|---|---|
| 멱등 | 같은 `task_id`·`revision` 을 다시 보내면 같은 핸들이 오고 파라미터도 안 덮인다 | `mimic` · `TaskRpcTest` · `멱등 재수신은 파라미터도 안 덮는다` |
| 멱등 — 발신자 둘 | 미믹이든 실제 하드웨어 어댑터든 같은 응답을 낸다 | `adapter-host` · `AdapterHostTest` · `같은 요청은 같은 핸들이고, 낮은 revision 은 거절이다` · `harness` · `HostParityTest` · `같은 키에 다른 스킬이 와도 둘이 같은 답을 낸다` |
| 멱등 — 하위 | 같은 참조로 두 번 맡겨도 운반은 하나다 | `picasso` · `DeliverContainerTest` · `같은 참조로 두 번 맡겨도 운반은 하나다 — 플릿 계약의 멱등` |
| 종료 래치 | 종착한 태스크는 무엇을 해도 종료에 머문다 | `harness` · `TerminalViolationTest` · `위반 뒤에 명령을 보내도 종착이다` |
| 종료 판정 일치 | 엔진의 모든 상태가 계약에서 같은 종료 판정을 받는다 | `mimic` · `TerminalParityTest` · `엔진의 모든 상태가 계약에서 같은 종착 판정을 받는다` |
| 순서 — 전송 | 전송이 늦어도 이벤트 순서는 안 바뀐다 | `harness` · `TransportFaultTest` · `지연은 순서를 안 바꾼다` |
| 순서 — 소비자 | 뒤섞여 와도 접은 최종 상태가 정상 순서와 같다 | `client` · `EventConsumerTest` · `재정렬 뒤 최종 상태가 정상 순서와 같다` |
| 번호 연속 | 스냅샷이 말하는 번호가 다음에 올 이벤트 번호다 | `mimic` · `EventServiceTest` · `스냅샷의 sequence가 다음에 올 번호다` |
| 잃은 것은 잃었다고 | 재생 버퍼를 벗어난 요청은 조용히 비지 않는다 | `adapter-host` · `AdapterHostTest` · `재생 버퍼를 벗어나면 SEQUENCE_EVICTED 다` |
| 거부 어휘 | 어댑터와 벤더의 거부가 계약의 코드 열넷 중 하나로 옮겨진다 | `adapter-host` · `AdapterHostTest` · `어댑터의 거절이 계약의 코드로 옮겨진다 — 모르는 이름은 PARAMETER_INVALID, 표면 부재는 CAPABILITY_WITHDRAWN` |
| 선언 밖은 안 통과 | 프로파일이 허용하지 않은 값은 거절된다 | `harness` · `CapabilityDifferenceTest` · `허용 값 밖의 ENUM은 거절된다` |
| 개정 순서 | 낮은 `revision` 은 `OUTDATED_REVISION` 이다 | `mimic` · `TaskRpcTest` · `핸들의 revision이 낮으면 OUTDATED_REVISION이다` |
| 식별 정보의 권위 | 헤더가 권위이고 페이로드의 `robot_id` 는 복사본이다 | `mimic` · `GetCapabilitiesTest` · `헤더가 권위이고 페이로드의 robot_id는 복사본이다` |
| 식별 정보 불일치 | 핸들과 헤더가 어긋나면 `IDENTITY_MISMATCH` 다 | `mimic` · `TaskRpcTest` · `핸들의 robot_id가 헤더와 다르면 IDENTITY_MISMATCH다` |
| 헤더 시퀀스 — 요청 | §5.5 의 요청 시퀀스를 정확히 따른다 | `contracts` · `WireTest` · `요청 헤더가 §5-5의 요청 열을 정확히 따른다` |
| 헤더 시퀀스 — 발행 | 발행 시퀀스는 요청 시퀀스와 다르고, 그 차이가 지켜진다 | `mimic` · `EventStreamTest` · `발행 헤더가 §5-5의 발행 열을 따른다` |
| 헤더를 손으로 안 짓는다 | 소비자에게 헤더를 직접 만들 자리가 없다 | `client` · `ClientBoundaryTest` · `헤더를 손으로 만들지 않는다` |
| 기종 불변 | 같은 `robot_id` 뒤에 다른 기종을 놓아도 오간 요청이 바이트 동일하다 | `harness` · `A1Test` · `같은 robot_id 뒤에 다른 기종을 놓아도 오간 요청이 바이트 동일하다` |
| 사전 조건 | 프로파일이 선언한 조건을 요청 시점의 파지 관측이 안 만족하면 **사우스바운드 호출 전에** `PRECONDITION_UNMET` 으로 거절한다. 관측 불가는 통과가 아니다 | `adapter-host` · `AdapterHostTest` · `쥔 채로 온 요청은 adapter accept 를 부르지 않는다` · `adapter-host` · `AdapterHostTest` · `관측 불가는 조건이 있는 스킬만 막는다` |
| 사전 조건 — 발신자 둘 | 미믹이든 실제 하드웨어 어댑터든 같은 코드·사유·조건 참조로 거절한다 | `harness` · `HostParityTest` · `쥔 채로 보낸 요청을 둘 다 같은 말로 거절한다` |

본 인터페이스 계약의 궁극적 목표는 **기종을 변경하거나 대체하더라도 통신 회선 상의 메시지 포맷과 동작이 불변(Invariant)을 유지하는 것**입니다.

## 4. 비보증 항목 (Non-Guarantees)

- **이벤트의 무한 전달 보장 배제**: 링 버퍼는 유한하며, 임계 초과 시 오래된 이벤트는 축출됩니다. 본 계약은 이벤트의 영구 보존이 아니라 **유실 발생 사실을 명시적으로 통보(`SEQUENCE_EVICTED`)함**을 보증합니다. 소비자는 이 경우 스냅샷을 통해 상태를 재동기화해야 합니다.
- **클록 절대 시각 불일치 허용**: 헤더 타임스탬프는 각 발신자의 로컬 시계 기준이며, 분산 환경의 시계 오차를 미들웨어가 일괄 보정하지 않습니다.
- **진행률 의미 보증 배제**: `ProgressBasis` 필드를 통해 수치와 함께 측정 근거를 전달합니다. 측정 근거가 상이한 두 수치는 단순 비교할 수 없으며, 관측 불가능(`NOT_OBSERVABLE`)한 경우 수치를 제공하지 않는 것이 정상 동작입니다.
- **기체 내부 상태의 래치 강제 불가**: 계약은 종료 상태 래치를 가상으로 집행하지 않으며, 실제 하드웨어 기체가 종료 신호 이후에도 비정상 구동할 경우 이를 계약 위반 결함(`Fault`)으로 탐지하여 상위에 보고합니다.

## 5. 신규 기종 어댑터 사전 적합성 검증 절차

코드 구현에 착수하기 전, 벤더 공식 명세만으로 계약 적합성을 사전에 정량 평가하는 절차입니다:

1. **벤더 인터페이스 API 표면 전수 추출**:
   - 벤더 1차 자료(Proto, IDL, OpenAPI, 공식 SDK)에서 심볼을 추출하여 `vendor-manifest.txt`에 식별자와 SHA-256 해시를 기록합니다.
   - 조사 범위(`survey_scope`)를 명시하여 누락된 서비스가 없는지 검증합니다.
2. **어휘 거리 측정 문서 작성**:
   - `profile/distance/<기종>.json`에 스킬별 도달 가능 여부(`reachable`), 벤더 프리미티브 매핑, 근거 등급(`evidence`)을 기록합니다.
   - 근거가 미확인된 항목은 `NO`가 아닌 `UNKNOWN`으로 선언합니다.
3. **기종 프로파일 정의**:
   - 거리 문서에서 `YES` 또는 `PARTIAL`로 판정된 스킬만을 프로파일 스펙 문서에 선언합니다.
4. **mimic 에뮬레이션 테스트**:
   - 작성된 프로파일을 기반으로 `mimic`을 구동하여 어댑터 구현 없이도 상위 시스템 클라이언트와의 계약 적합성(RPC, 이벤트, 종료 전이)을 선행 검증합니다.
5. **요구-케이퍼빌리티 협상 판정**:
   - `capability` 모듈의 `Negotiator`를 통해 상위 작업 요구조건과 기종 프로파일 간의 호환성을 사전 판정합니다.

## 6. 품질 게이트 및 케이퍼빌리티 프로젝션 구조

- **게이트 단일 구현**: CI 환경과 런타임 레지스트리 등록 검증은 동일한 `gate` 라이브러리를 호출하여 검증 일관성을 유지합니다.
- **케이퍼빌리티 프로젝션 필터링**: 프로파일 내 13개 최상위 메타데이터 중 소비자의 실행 판단에 필요한 핵심 8개 필드만이 런타임 `Capability` 객체로 투영되며, 관리용 필드는 제외됩니다.

## 7. 소유 이전의 전제: 재기동과 넘겨받기

본 절은 보장이 아닌 전제 검토로서, 재기동과 소유 이전 과정에서 각 명령이 무엇에 기대며 시험이 무엇을 확인하는지 기술한다. 현재 미들웨어 `Middleware`, `adapter-host`의 `HostedRobot`, 에뮬레이터(`mimic`)의 세 영역 상태는 모두 프로세스 메모리에만 존재하며 영속 저장소는 없다. 설계 범위상 프로세스 재기동 뒤 저장소 기반 상태 복원은 제외되고 `IN_DOUBT` 해소 경로는 범위에 포함되며(설계 §1.3 B-1), 어댑터 재시작 뒤 매핑은 범위 밖이다([`scenarios.md`](scenarios.md) §7 ⑤). 각 항목은 «검증됨(같은 프로세스)»(단일 프로세스 내부 실행 시험), «검증됨(재기동, 같은 소유자)»(동일 소유자 재기동 실행 시험), «미검증»(동작을 단언하는 시험 없음)의 세 표시로 구분한다. `IN_DOUBT`, 근거 등급, `Middleware.resume`은 계약 proto로 전달되지 않는 계약 밖 미들웨어 계층이다.

### 7.1 명령별 전제 표

- `StartTask` 상세
  - 저장 주체: [미들웨어] 단위의 태스크 id와 요청 시각을 발송 전 메모리에 보관한다. 하위 태스크 id는 작업 지시에서 결정적으로 유도된다(`작업지시id#단위id`, 재작업 시 `@rN`). [하위] `adapter-host`는 벤더 호출(`adapter.accept`) 뒤에 태스크 장부(`book`)에 기록하며 에뮬레이터도 메모리에 보관한다.
  - 멱등 키와 수명: 키는 `(task_id, revision)`이다. 단일 프로세스 내부에서는 두 발신자 모두 이를 준수한다(검증됨(같은 프로세스)). 미들웨어 재기동을 넘어서는 하위가 유지되면 준수된다(`Middleware.resume`, §7.3). `adapter-host` 재시작을 넘어서면 장부가 비어 동일 키가 새 수락으로 처리되고 벤더 호출이 재발송된다(코드 판독, 미검증: 단언 시험 없음). 대다수 벤더는 클라이언트 참조 키를 수신하지 않는다.
  - 재기동 뒤 조회: 미들웨어의 `IN_DOUBT` 최초 조회는 동일 요청의 재전송이다. `adapter-host`가 재시작된 경우 이 조회가 새 명령이 된다.
  - 완료 근거: 수락 응답은 완료가 아니며 최종 종료는 `WatchTask`로 수신된다.
  - 확인 불가 시 정책: [미들웨어] 응답 유실 시 `IN_DOUBT`로 전이한다. 새 명령으로 다시 발송하지 않는다. 조회 재시도(기본 3회) 뒤 설비 관측을 수행하여 유예 범위 내이면 잠정 완료로 운영자에게 전달하고, 초과 시 운영자에게 전달한다. 자동 재실행은 없으며 재수행은 사람의 재작업(ADR 47)으로 처리한다.

- `WatchTask` 상세
  - 저장 주체: [하위] 발신자는 태스크별 갱신 로그를 메모리에 유지한다. [미들웨어] `ClientRobotPort`는 수신한 갱신을 누적 보관하고, 단위가 닫히면 미들웨어가 `RobotPort.release`를 불러 그 태스크의 누적 목록과 팔로워를 지운다. 닫히는 경로를 지나지 않고 버려진 실행의 항목은 남는다(검증됨(같은 프로세스): `picasso` · `EventStreamTest` · `끝난 단위의 태스크는 포트의 갱신 표에서 내린다`).
  - 멱등 키와 수명: 키는 `task_id` + `update_index`(태스크마다 0부터 시작)이다. 진행률 단조성은 `(task_id, revision, attempt)` 구간 내부에서만 성립한다.
  - 재기동 뒤 조회: `from_update_index`로 이어받는다. 범위 초과는 `OUT_OF_RANGE`, 미등록 태스크는 `NOT_FOUND`를 반환한다. `adapter-host` 재시작 뒤에는 항상 `NOT_FOUND`가 반환되며, `ClientRobotPort`는 스트림이 `NOT_FOUND`·`OUT_OF_RANGE`로 닫히면 다시 붙지 않고, 기한 초과와 연결 단절에만 다시 붙는다(검증됨(같은 프로세스): `picasso` · `StreamResumeTest` · `기체가 모르는 태스크면 다시 붙지 않는다`).
  - 취소 효력: 종료 수신 시 스트림이 닫힌다.
  - 완료 근거: 최종 갱신이 `SUCCEEDED`이면 미들웨어가 근거 등급 E0로 수락하고 근거 결합을 시작한다.
  - 확인 불가 시 정책: [미들웨어] 스트림 복구가 끝내 실패하면 단위는 `RUNNING`에 머문다. 정체 알림은 진행률을 측정하는 기체에서만 발생하며 상태를 변경하지 않는다. 따라서 `adapter-host` 재시작으로 태스크를 유실하면 `IN_DOUBT`로 전이하는 경로가 없다(코드 판독, 미검증: 단언 시험 없음).

- `CancelTask` 상세
  - 저장 주체: [미들웨어] 취소 요청, 최종 취소, 거부 코드를 메모리에 유지한다. [하위] 태스크 로그에 `CANCELLING`과 종료를 기록한다.
  - 멱등 키와 수명: 키는 `TaskHandle`이다. 재취소는 멱등이다(검증됨(같은 프로세스): `mimic` · `EngineListenerTest` · `멱등 재취소는 전이를 보고하지 않는다`).
  - 재기동 뒤 조회: 취소 결과는 `WatchTask`의 종료 상태와 `hold`로 확인한다.
  - 취소 효력: 즉시가 아니다. `CANCELLING` 뒤 `CANCELLED`(복구 마침) 또는 `CANCELLED_RECOVERY_FAILED`(적재 상태 정지)로 전이한다. `CANCELLED`와 `HOLDING`은 함께 오지 않는다. 하위 수단 부재 시 `CANCEL_UNSUPPORTED`, 기종료 태스크면 `INVALID_TRANSITION`을 반환한다. 미들웨어는 현재 핸들에만 발송하며 거부되면 진행 중 단위는 경계까지 실행 후 정지한다. 설비 대기는 미들웨어가 직접 종료한다.
  - 완료 근거: 취소 보고(`CancelReport`)의 정리 결과(`cleanup`)는 계약 종료 상태에서 판정한다. 정리 실패 시 운영자 개입이 필요하다. 보고의 `accepted`와 `motionStopped`는 항상 `true`인 상수다(관측 근거 없음, 미검증, §7.2 (e)).
  - 확인 불가 시 정책: [미들웨어] `IN_DOUBT` 진행 중의 취소는 핸들이 생성되는 즉시 하위에 전달된다.

- `RetryTask` 상세
  - 동작 및 시험: 에뮬레이터는 재시도마다 `attempt`를 증가시킨다(검증됨(같은 프로세스): `harness` · `RetryTest` · `재시도가 attempt를 올린다`). `adapter-host`는 갱신과 스냅숏에 `attempt`를 항상 0으로 싣는다.
  - 확인 불가 시 정책: 어댑터의 재시도 기본 구현은 수단 없음이며 재정의한 어댑터가 없어 `adapter-host`에서는 `INVALID_TRANSITION`이다. 미들웨어는 `RetryTask`를 호출하지 않는다. `RETRIABLE`과 `NEEDS_INTERVENTION`을 단위의 종료로 판정하며, 재수행은 사람의 재작업(`@rN`)으로 처리하므로 소유 이전 경로에 포함되지 않는다.

- `PauseTask` / `ResumeTask` 상세
  - 동작 및 정책: 계약에 정의되어 있으나 `adapter-host`의 재개 기본 구현은 수단 없음이며 재정의한 어댑터가 없다. 미들웨어는 두 명령 모두 호출하지 않으며 소유 이전 경로 밖이다.

- `GetSnapshot` 상세
  - 저장 주체 및 키: 발신자 메모리에 저장되며 키는 `session_id` + `sequence`(다음에 올 이벤트 번호)이다. 프로세스 내부에서는 재생 버퍼 초과로 미전송 이벤트를 축출할 때만 세션이 변경된다. 계약은 재기동 시 신규 세션으로 전제하나, `adapter-host`의 세션은 프로세스 내부 카운터여서 재시작마다 동일 값이 반복될 수 있다([`limits.md`](limits.md) §15.21).
  - 재기동 뒤 조회로 알 수 있는 것: 현재 장부의 태스크 상태(에뮬레이터 및 `adapter-host`는 종료한 태스크도 포함하나 계약상 미규정, [`limits.md`](limits.md) §15.221 · 기록이 들지 않는 것), 활성 결함(확인 실패 시 `UNAVAILABLE`), 연결 상태, 다음 번호를 알 수 있다. 반면 재시작 전 수락한 태스크와 재시작 전 이벤트는 알 수 없다(누락).
  - 확인 불가 시 정책: [미들웨어] 스냅숏을 읽지 못하면 관측 불가로 처리하고 단절 판정을 건너뛴다. `Middleware.resume`은 실행을 생성하지 않고 거부한다.

- `ReplayEvents` 상세
  - 동작 및 전제: 버퍼를 벗어난 요청에는 `SEQUENCE_EVICTED`로 응답한다(§3 «잃은 것은 잃었다고»).
  - 재기동 뒤 조회: 재기동 뒤 이전 커서(다음 번호 초과 값)로 요청하면 두 발신자 모두 빈 응답을 반환하며 축출로 응답하지 않는다(코드 판독, 계약 미규정, 미검증: 단언 시험 없음).
  - 확인 불가 시 정책: [미들웨어] 미들웨어 스냅숏 모델에 세션 칸(`RobotSnapshot.session`, 응답 헤더의 `session_id`)이 있고, 미들웨어는 세션이 앞서 읽은 것과 다르면 커서를 그 스냅숏의 번호로 다시 세운다(검증됨(같은 프로세스): `picasso` · `EventStreamTest` · `하위가 다시 떠 세션이 바뀌면 옛 커서를 버리고 스냅샷부터 다시 세운다`). 이 시험에서 하위 재기동은 시험 더블이 흉내 낸다. 다만 `adapter-host`의 세션이 재시작마다 같은 값으로 되풀이되면 미들웨어가 재시작을 보지 못해 낡은 커서가 새 세션의 앞 이벤트를 건너뛴다(코드 판독, [`limits.md`](limits.md) §15.215 · 옛 커서). 이벤트는 자취 기록 전용이며 상태 판정은 `WatchTask`를 기준으로 수행한다.

- `GetCapabilities` 상세
  - 프로젝션 및 캐시: 프로젝션은 프로파일에서 온다. 클라이언트는 `capability_epoch`로 캐시 유효성을 판정한다(검증됨(같은 프로세스): `client` · `ClientTest` · `세대가 바뀌면 캐시를 버린다`).
  - 에포크 단조성: 에포크 단조성은 프로세스 내부에서만 유지된다(검증됨(같은 프로세스): `harness` · `DegradationTest` · `복원해도 epoch는 되돌아가지 않는다`).
  - 재기동 뒤 조회: 재기동 시 에뮬레이터는 1로 복귀하고 `adapter-host`는 항상 1이다. 케이퍼빌리티 에포크는 소유 세대가 아니다.
  - 확인 불가 시 정책: [미들웨어] 케이퍼빌리티 조회가 실패하면 선택 파라미터를 추가하지 않는다.

### 7.3 같은 소유자가 다시 뜰 때(A=B)

- 있는 것: 미들웨어 재기동. `Middleware.resume(작업 지시, 기체, 임무 정의·버전)` 이 담는 쪽의 기록으로 같은 정체성의 실행을 새로 짓는다. 상태 복원이 아니다. 근거 시험은 §7.2 (a)(b)(f) 의 `ResumeTest`. 기체는 재기동 전 태스크를 든 시험 더블이다. `Middleware.resume` 은 판단 기록을 선택 입력으로 받고, 받으면 운영자 판단, 감수한 결함, 승인 소모, 요청 시각(근거 윈도우와 설비 대기 기한 시작), 검증 대기 창, 이전 판정이 넘어오며 다시 판정하지 않는다. 기록이 다른 작업 지시나 버전의 것이면 거부한다. 운영자 보류 단위는 다시 지은 인스턴스가 인시던트를 새로 열고(표시 `RESUME_HOLD_REOPENED`), 그 인시던트에 낸 판단이 보통의 보류처럼 보류를 풀고 판단 기록에 실린다(`picasso` · `JudgmentRecordTest` · `기록의 운영자 보류로 다시 지은 단위는 다시 열었다고 적은 인시던트 하나를 이 인스턴스에 연다`, `picasso` · `JudgmentRecordTest` · `다시 연 인시던트에 낸 판단이 보류를 풀고 그 인시던트와 판단 기록에 실린다`, `picasso` · `JudgmentRecordTest` · `운영자 보류가 아닌 판정으로 다시 지은 단위는 인시던트를 열지 않는다`, `picasso` · `JudgmentRecordTest` · `이미 다시 지은 실행에 resume 을 다시 불러도 인시던트를 겹쳐 열지 않는다`). 다시 연 인시던트 번들의 `at` 은 `resume` 이 시계를 한 번 읽어 모든 해당 줄과 그 봉인의 `at` 에 같은 시각을 쓰므로 시계가 읽을 때마다 흘러도 그 단위의 `RESUME_HOLD_REOPENED` 줄 시각과 같다. 따라서 읽는 쪽은 그 줄이 단순히 근거 윈도우에 들었는지가 아니라 줄 시각이 `at` 과 같은지로 다시 연 인시던트를 가려내며(다시 연 뒤 근거 윈도우 앞 폭 안에 새로 선 보류도 그 줄을 싣는다), 따로 실제 시계를 읽는 `wallClockAt` 은 이에 해당하지 않는다(`picasso` · `JudgmentRecordTest` · `시계가 읽을 때마다 흘러도 다시 연 인시던트마다 at 이 그 단위의 다시 연 줄 시각과 같다`, `picasso` · `JudgmentRecordTest` · `다시 연 뒤 근거 윈도우 앞 폭 안에 새로 선 보류는 그 줄을 싣지만 at 이 줄 시각과 달라 다시 연 것으로 읽히지 않는다`). 근거 시험은 `JudgmentRecordTest` 와 `JudgmentRecordWireTest` 이고 기체는 시험 더블, 미들웨어만 재기동, 승인 소모 시험만 에뮬레이터 위에서 돈다. 판단 기록은 계약 밖 미들웨어 계층이고 계약 proto 와 SemVer 0.9.0 은 그대로다.
- 전제 셋(어느 하나라도 깨지면 위 시험이 말하는 바가 없다):
  1. 담는 쪽이 이전 인스턴스가 받은 마지막 버전의 작업 지시와 임무 정의·버전을 들고 있다. 그 저장 입구는 picasso 에 없다. 판단 기록도 담는 쪽이 들고 있어야 넘어온다. picasso 에는 그 기록을 내고 받는 입구만 있고 영속 입구는 없다.
  2. 하위(`adapter-host`)는 재기동하지 않았다. 재작업 횟수를 스냅숏의 태스크 id 접미사에서 되찾고, 같은 id 재전송이 기존 핸들에 붙는 계약 멱등에 기댄다.
  3. 하위가 종료한 태스크를 스냅숏에 싣는다. 계약은 정하지 않는다(에뮬레이터·`adapter-host` 는 싣는다). 이 전제는 기록에 판정이 없는 단위(또는 기록 없이 다시 지을 때)에만 남는다.
- 기록 없이 다시 지을 때 넘어오지 않는 것: 운영자 판단, 감수한 결함, 승인 소모 기록, 근거 윈도우 요청 시각, 설비 대기 기한 시작 시각, 이전 근거 확인 결과. 작업 응답 아웃박스의 미확인 응답도 메모리다. 마지막 로봇 태스크 앞 단위는 근거 등급 E0 로 닫혀 요구가 E2 면 요구에 못 미친 채 정착한다. 첫 소비자인 picasso-ops 는 판단 기록을 영속해 재기동 때 `resume` 에 넘긴다(picasso-ops PR #38, 설계 문서 §15.223). 이 거동은 이제 (i) 기록을 넘기지 않는 경우(기록을 영속하지 않는 담는 쪽이나 기록 테이블이 생기기 전에 받은 picasso-ops 저널 행), (ii) 기록 쓰기에 실패한 뒤 낸 판단에서 다음 성공 쓰기 전에 프로세스가 죽는 경우의 둘에만 남는다.
- 기록을 넘겨도 넘어오지 않는 것: 작업 응답 아웃박스의 미확인 응답, 이전 인스턴스의 인시던트(보류 단위는 새로 연다)와 조치 탐색 레지스터, 같은 조치의 승인 횟수, 파지 관측과 조회 횟수 같은 관측값이다([`limits.md`](limits.md) §15.221 · 기록이 들지 않는 것).
- 스냅숏은 단위가 묶인 기체마다 읽고 하나라도 못 읽으면 거부하며 실행을 만들지 않는다(오늘은 한 기체라 한 번). 근거 시험은 `picasso` · `UnitRobotBindingTest` · `다시 짓기는 단위마다 그 기체의 스냅숏을 읽고 하나라도 못 읽으면 미룬다`, `picasso` · `ResumeTest` · `스냅숏을 못 읽으면 거부하고 실행을 만들지 않는다` 이다.
- 없는 것: `adapter-host` 재시작. 장치도 시험도 없고 범위 밖이다([`scenarios.md`](scenarios.md) §6 시나리오 3, §7 ⑤).

### 7.4 다른 프로세스가 넘겨받을 때(A≠B): 지금 없는 것

아래는 보장이 아니다. 넘겨받기 순서(권한 획득, 옛 발행 경로 차단, 진행 중 명령과 물리 상태 대조, 발행 재개)마다 지금 코드에 있는 것과 빈자리를 적는다.

| 순서 | 지금 코드 | 빈자리 |
| :--- | :--- | :--- |
| 1. 권한 획득 | 미들웨어에 잠금·리스·리더 선출이 없다. `instanceId`(`mw-` + 무작위 UUID)는 작업 응답 내보내기에만 실리고 하위로 안 나간다. 자원 소유 레지스터([`orchestration.md`](orchestration.md) §2)에 명령 발행 경로의 소유 인스턴스 행이 없다. | 지금 소유자를 정하는 장치. |
| 2. 옛 경로 차단(수신자 쪽 세대 대조) | 헤더에 소유자·세대 칸이 없다. `client_id` 는 실리지만 두 수신자 모두 읽지 않는다. 라우팅은 계약 리비전과 `robot_id` 만 보고, 조작은 태스크 id 만 맞으면 누구의 요청이든 받는다. `capability_epoch` 는 케이퍼빌리티 에포크이지 소유 세대가 아니다. 벤더 쪽 리스는 한 기종에만 있다. | 수신자(`adapter-host`)가 세대를 대조하는 자리(벤더가 대조하지 않는 기종이 있으므로). |
| 3. 보내기 전 의도 기록 | 하위 태스크 id 가 결정적이라 작업 지시만 있으면 다시 유도된다. 이것이 지금 의도 기록 노릇을 하는 유일한 것이다. 보내기 전 의도는 미들웨어 메모리에만 있고 `adapter-host` 에는 없다(벤더 호출 뒤에 장부 기록). | «벤더는 받았는데 기록 전에 죽음» 을 구분하는 보내기 전 의도 기록. |
| 4. 벤더 매핑 영속 | `(task_id, revision)` 과 벤더 id 의 매핑이 어댑터 메모리에만 있다([`scenarios.md`](scenarios.md) §7 ⑤). | 그 매핑의 영속. |
| 5. 재시작 뒤 진행 중 벤더 태스크 들이기 | `adapter-host` 재시작 뒤 펌프는 지금 태스크(`current`)만 어댑터에 묻는다. 벤더에서 아직 도는 태스크는 장부·스냅숏에 없고 배타 검사도 못 본다. 결함만 다시 관측된다. | 재시작 직후 벤더의 «지금 도는 것» 을 장부로 들이는 단계. |
| 6. 판단·승인 이관과 발행 재개 | `Middleware.resume` 은 관문을 다시 걸지 않고 다음 pump 에서 바로 발행한다. 넘겨받는 쪽은 판단 기록(`JudgmentRecord`)을 받으면 운영자 판단·감수한 결함·승인 소모·시각·판정을 이관해 재개할 수 있고, 담는 쪽이 그 기록을 영속하지 않으면 전처럼 그것 없이 재개한다. 첫 소비자인 picasso-ops 는 기록을 영속해 같은 프로세스의 재기동 때 넘긴다(설계 문서 §15.223). | 재개 전 «이전 소유자의 발행이 멈췄다» 는 확인. picasso-ops 의 하트비트는 리스가 아니므로(세대나 펜싱이 없고 만료 뒤 깨어난 프로세스를 멈추지 못함) 이 확인을 채우지 못한다. |
| 7. 공통: 재기동 신호 | `adapter-host` 세션이 재시작마다 되풀이될 수 있고(§15.21), 미들웨어는 이제 세션이 바뀌면 커서를 다시 세우지만 세션이 되풀이되면 재시작을 보지 못하며, 옛 커서에 발신자가 빈 응답을 준다. 이력(인시던트·조치 탐색·승인 소모 적재 §15.166, 재생 버퍼 §15.8)도 메모리다. | 발신자가 새 프로세스를 확실히 알리고 소비자가 그것을 읽는 것. |

이 절의 «미검증» 과 빈자리는 [`limits.md`](limits.md) 의 해당 행이 추적한다(§15.8, §15.21, §15.166, §15.221 · 기록이 들지 않는 것, §15.215 행들, §15.228 · 영구 스트림 실패).
