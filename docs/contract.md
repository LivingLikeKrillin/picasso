# 인터페이스 계약 명세서 — 계약 보증 규격 및 진입 기준

`picasso/v1`은 본 미들웨어 시스템의 유일한 **공개 인터페이스 면(Public Surface)**입니다. 상위 시스템 소비자는 본 계약 인터페이스만을 참조하며, 하위 로봇 어댑터는 본 인터페이스 규격을 구현합니다.

본 문서는 본 계약에 **어떤 항목이 진입할 수 있는지(진입 기준)**, 그리고 진입한 인터페이스가 **시스템적으로 어떤 성질을 보증하는지(계약 담보 사항)**를 규정합니다.

- 컴포넌트 교체 지점 명세: [`seams.md`](seams.md)
- ISA-95 상류 표준 데이터 모델 연계: [`isa95.md`](isa95.md)
- 구간별 검증 수준 및 환경 신뢰도: [`verification.md`](verification.md)

## 1. 인터페이스 계약 진입 기준 (2대 관문)

신규 필드, RPC 메서드, 에러 코드가 계약에 추가되기 위해서는 다음 두 가지 기준을 반드시 충족해야 합니다:

### 1.1 관문 1: 소비처 실재 원칙 (ADR 9)
- **실제 소비자가 존재하지 않는 사양은 선언하지 않습니다.**
- 인터페이스 선언이 공개되는 즉시 소비자는 해당 필드의 가용성을 전제하기 시작하므로, 이후 제거 시 호환성 파괴(Breaking Change)가 발생합니다.
- 예: 파지 실패를 거절 코드로 선언하려던 시도는 벤더가 이를 사전 선언이 아닌 런타임 피드백으로만 통보한다는 점이 확인되어 배제되었습니다 (§15.79).

### 1.2 관문 2: 표준 및 기존 어휘 기반 원칙 (ADR 36)
- **상위 시스템 표준 또는 로봇 벤더 표면 중 최소 한쪽에 이미 존재하는 개념만을 수용합니다.**
- 양쪽 어디에도 존재하지 않는 임의 어휘는 번역(Translation)이 아닌 시스템 창작(Invention)이 되어 현장 적용 시 정합성이 결여됩니다.
- 수명주기(Lifecycle) 및 제어 권한(Lease)은 양측에 공통으로 존재하여 채택되었습니다. 반면, 자체 정의했던 스킬 카탈로그는 양측 모두에 부재하여 실물 정합성 검증을 통과하지 못했습니다 (ADR 36).
- `skill_catalog.proto`는 메이저 버전 하위 호환성 유지를 위해 프로토콜에 잔류하고 있으며, 지금도 스킬 타입 **넷**이 거기 있다 (ADR 36 결정 4). 다만, 신규 인터페이스 설계 시 이러한 계층 혼용을 엄격히 배제합니다.
- 복수 기종이 공통 지원한다고 해서 좋은 계약 요소인 것은 아닙니다. 예컨대 `move_relative`는 보편적으로 지원되나, 배정이 아닌 저수준 모터 실행 계층에 속하므로 상위 계약 요소로 부적합합니다.

## 2. 계약 제외 항목 (Out-of-Scope) 및 분리 근거

| 계약 제외 항목 | 제외 근거 | 책임 계층 및 처리 방식 |
|---|---|---|
| **하드웨어 비상정지·보호정지·사람 감지** | ADR 32 — 안전 기능은 미들웨어 소프트웨어 가용성과 물리적으로 격리되어야 함 | 독립 하드웨어 안전 루프 (Safety PLC) |
| **명령 왕복 지연(RTT) 상한 보증** | ADR 32 — 본 인터페이스 면은 엄격한 실시간성(Hard Real-time)을 보장하지 않음 | 제어 루프 내부 (계약 외 범위) |
| **현장 시설물 제약 (도어 개폐, 조도 등)** | 로봇의 실제 역량은 기체 단독이 아닌 `(기체 × 현장 인프라)`의 결합 속성임 | [`environment-preconditions.md`](environment-preconditions.md) |
| **작업 배차 및 로봇 할당 결정** | ADR 36 계층 ③ | 미들웨어 오케스트레이션 코어 (`picasso`) |
| **벤더 미션 시퀀스 조합 및 제어 정밀도** | ADR 36 계층 ⑤ — 상류 시스템에 대한 내부 세부사항 은닉 | 로봇 어댑터 내부 |
| **시설물 명칭과 로봇 내부 좌표 매핑** | ADR 34·35 — 시맨틱 결속의 책임 주체는 로봇 기체 자체임 | 로봇 내부 (현장 맵 등록 작업) |

> **설계 원칙:** 안전 기능(E-Stop 등)을 소프트웨어 계약 위에 통합할 경우, 버퍼링 및 세션 재연결 메커니즘을 통과하게 되어 치명적인 지연을 초래하므로 원천 분리합니다.

## 3. 계약 담보 사항 및 자동화 검증 매핑

모든 계약 보증 사항은 이를 증명하는 자동화 테스트와 1:1로 결속되어야 합니다. `DocumentClaimsTest`가 본 표의 테스트 클래스 및 메서드 존재 여부를 자동으로 대조 검증합니다.

| 담보 | 무엇을 약속하나 | 지키는 시험 |
|---|---|---|
| 멱등 | 같은 `task_id`·`revision` 을 다시 보내면 같은 핸들이 오고 파라미터도 안 덮인다 | `mimic` · `TaskRpcTest` · `멱등 재수신은 파라미터도 안 덮는다` |
| 멱등 — 발신자 둘 | 미믹이든 실물 어댑터든 같은 답을 낸다 | `adapter-host` · `AdapterHostTest` · `같은 요청은 같은 핸들이고, 낮은 revision 은 거절이다` |
| 멱등 — 하류 | 같은 참조로 두 번 맡겨도 운반은 하나다 | `picasso` · `DeliverContainerTest` · `같은 참조로 두 번 맡겨도 운반은 하나다 — 플릿 계약의 멱등` |
| 종착 래치 | 종착한 태스크는 무엇을 해도 종착에 머문다 | `harness` · `TerminalViolationTest` · `위반 뒤에 명령을 보내도 종착이다` |
| 종착 판정 일치 | 엔진의 모든 상태가 계약에서 같은 종착 판정을 받는다 | `mimic` · `TerminalParityTest` · `엔진의 모든 상태가 계약에서 같은 종착 판정을 받는다` |
| 순서 — 전송 | 전송이 늦어도 이벤트 순서는 안 바뀐다 | `harness` · `TransportFaultTest` · `지연은 순서를 안 바꾼다` |
| 순서 — 소비자 | 뒤섞여 와도 접은 최종 상태가 정상 순서와 같다 | `client` · `EventConsumerTest` · `재정렬 뒤 최종 상태가 정상 순서와 같다` |
| 번호 연속 | 스냅샷이 말하는 번호가 다음에 올 이벤트 번호다 | `mimic` · `EventServiceTest` · `스냅샷의 sequence가 다음에 올 번호다` |
| 잃은 것은 잃었다고 | 재생 버퍼를 벗어난 요청은 조용히 비지 않는다 | `adapter-host` · `AdapterHostTest` · `재생 버퍼를 벗어나면 SEQUENCE_EVICTED 다` |
| 거절 어휘 | 어댑터와 벤더의 거절이 계약의 코드 열넷 중 하나로 옮겨진다 | `adapter-host` · `AdapterHostTest` · `어댑터의 거절이 계약의 코드로 옮겨진다 — 모르는 이름은 PARAMETER_INVALID, 표면 부재는 CAPABILITY_WITHDRAWN` |
| 선언 밖은 안 통과 | 프로파일이 허용하지 않은 값은 거절된다 | `harness` · `CapabilityDifferenceTest` · `허용 값 밖의 ENUM은 거절된다` |
| 개정 순서 | 낮은 `revision` 은 `OUTDATED_REVISION` 이다 | `mimic` · `TaskRpcTest` · `핸들의 revision이 낮으면 OUTDATED_REVISION이다` |
| 신원의 권위 | 헤더가 권위이고 페이로드의 `robot_id` 는 복사본이다 | `mimic` · `GetCapabilitiesTest` · `헤더가 권위이고 페이로드의 robot_id는 복사본이다` |
| 신원 불일치 | 핸들과 헤더가 어긋나면 `IDENTITY_MISMATCH` 다 | `mimic` · `TaskRpcTest` · `핸들의 robot_id가 헤더와 다르면 IDENTITY_MISMATCH다` |
| 헤더 열 — 요청 | §5.5 의 요청 열을 정확히 따른다 | `contracts` · `WireTest` · `요청 헤더가 §5-5의 요청 열을 정확히 따른다` |
| 헤더 열 — 발행 | 발행 열은 요청 열과 다르고, 그 차이가 지켜진다 | `mimic` · `EventStreamTest` · `발행 헤더가 §5-5의 발행 열을 따른다` |
| 헤더를 손으로 안 짓는다 | 소비자에게 헤더를 직접 만들 자리가 없다 | `client` · `ClientBoundaryTest` · `헤더를 손으로 만들지 않는다` |
| 기종 불변 | 같은 `robot_id` 뒤에 다른 기종을 놓아도 오간 요청이 바이트 동일하다 | `harness` · `A1Test` · `같은 robot_id 뒤에 다른 기종을 놓아도 오간 요청이 바이트 동일하다` |
| 사전 조건 | 프로파일이 선언한 조건을 요청 시점의 파지 관측이 안 만족하면 **남쪽 호출 전에** `PRECONDITION_UNMET` 으로 거절한다. 관측 불가는 통과가 아니다 | `adapter-host` · `AdapterHostTest` · `쥔 채로 온 요청은 adapter accept 를 부르지 않는다` · `adapter-host` · `AdapterHostTest` · `관측 불가는 조건이 있는 스킬만 막는다` |
| 사전 조건 — 발신자 둘 | 미믹이든 실물 어댑터든 같은 코드·사유·조건 참조로 거절한다 | `harness` · `HostParityTest` · `쥔 채로 보낸 요청을 둘 다 같은 말로 거절한다` |

본 인터페이스 계약의 궁극적 목표는 **기종을 변경하거나 대체하더라도 통신 와이어 상의 메시지 포맷과 거동이 불변(Invariant)을 유지하는 것**입니다.

## 4. 비보증 항목 (Non-Guarantees)

- **이벤트의 무한 전달 보장 배제**: 링 버퍼는 유한하며, 임계 초과 시 오래된 이벤트는 축출됩니다. 본 계약은 이벤트의 영구 보존이 아니라 **유실 발생 사실을 명시적으로 통보(`SEQUENCE_EVICTED`)함**을 보증합니다. 소비자는 이 경우 스냅샷을 통해 상태를 재동기화해야 합니다.
- **클록 절대 시각 불일치 허용**: 헤더 타임스탬프는 각 발신자의 로컬 시계 기준이며, 분산 환경의 시계 오차를 미들웨어가 일괄 보정하지 않습니다.
- **진행률 의미 보증 배제**: `ProgressBasis` 필드를 통해 수치와 함께 측정 근거를 전달합니다. 측정 근거가 상이한 두 수치는 단순 비교할 수 없으며, 관측 불가능(`NOT_OBSERVABLE`)한 경우 수치를 제공하지 않는 것이 정상 거동입니다.
- **기체 내부 상태의 래치 강제 불가**: 계약은 종착 상태 래치를 가상으로 집행하지 않으며, 실물 기체가 종착 신호 이후에도 비정상 구동할 경우 이를 계약 위반 결함(`Fault`)으로 탐지하여 상위에 보고합니다.

## 5. 신규 기종 어댑터 사전 적합성 검증 절차

코드 구현에 착수하기 전, 벤더 공식 명세만으로 계약 적합성을 사전에 정량 평가하는 절차입니다:

1. **벤더 인터페이스 표면 전수 추출**:
   - 벤더 1차 자료(Proto, IDL, OpenAPI, 공식 SDK)에서 심볼을 추출하여 `vendor-manifest.txt`에 식별자와 SHA-256 해시를 기록합니다.
   - 조사 범위(`survey_scope`)를 명시하여 누락된 서비스가 없는지 검증합니다.
2. **어휘 거리 측정 문서 작성**:
   - `profile/distance/<기종>.json`에 스킬별 도달 가능 여부(`reachable`), 벤더 프리미티브 매핑, 근거 등급(`evidence`)을 기록합니다.
   - 근거가 미확인된 항목은 `NO`가 아닌 `UNKNOWN`으로 선언합니다.
3. **기종 프로파일 정의**:
   - 거리 문서에서 `YES` 또는 `PARTIAL`로 판정된 스킬만을 프로파일 스펙 문서에 선언합니다.
4. **mimic 에뮬레이션 테스트**:
   - 작성된 프로파일을 기반으로 `mimic`을 구동하여 어댑터 구현 없이도 상위 시스템 클라이언트와의 계약 적합성(RPC, 이벤트, 종착 전이)을 선행 검증합니다.
5. **요구-능력 협상 판정**:
   - `capability` 모듈의 `Negotiator`를 통해 상위 일감 요구조건과 기종 프로파일 간의 호환성을 사전 판정합니다.
