# ADR 37 — 기체 등록 경로의 이원화: 플릿 자동 발견 vs 운영자 수동 선언

- **설계 문서 참조**: §15.77, §15.101, §15.105, ADR 31, ADR 33
- **결정 일자**: 2026-09-09 (2026-09-10 구현 완료)
- **상태**: 결정됨 (코드베이스 반영 완료)

---

## 1. 맥락 및 배경

로봇 어댑터가 연동되는 물리적 위치는 기종에 따라 상이합니다. Spot, Digit, G1 등은 로봇 제어기에 직접 연결되지만, Boston Dynamics Orbit과 같은 시스템은 상위 플릿 매니저(Fleet Manager)를 경유하여 연결됩니다.

초기에는 기종 프로파일에 `attachment: ROBOT_DIRECT | FLEET_MANAGER` 필드를 추가하여 런타임에 노출하자는 제안이 있었으나, 이는 벤더의 물리 배포 형태가 상류 클라이언트 코드의 조건 분기(`if attachment == FLEET_MANAGER`)로 누출되므로 기각되었습니다 (ADR 36 결정 5 위반).

그러나 두 연동 방식 간의 본질적 차이는 **"기체 목록의 소유권과 등록 절차"**에 명확히 존재합니다:
- **플릿 경유 방식**: 플릿 매니저가 기체 목록을 보유하고 있으며, 어댑터가 이를 **동적으로 발견(Discovery)**하여 등록.
- **로봇 직결 방식**: 개별 로봇의 네트워크 주소를 운영 엔지니어가 **사전에 수동 선언(Declaration)**하여 등록.

---

## 2. 핵심 결정 사항

**"기체 등록 절차의 이원화를 수용하되, 이를 페이로드의 인위적 타입 필드가 아닌 인입되는 HTTP 엔드포인트 게이트웨이로 엄밀히 분리한다."**

| 등록 경로 | 인입 HTTP 엔드포인트 | 인증 토큰 체계 | 등록 데이터 성격 |
|---|---|---|---|
| **동적 발견 (Discovery)** | `POST /ingest/robots?site=` | 기체 적재 토큰 (`IngestToken`) | 시스템 관측 보고 (Observation) |
| **수동 선언 (Declaration)** | `POST /operations/robots` | 운영자 관리 토큰 (`OperatorToken`) | 인간 엔지니어의 정책 판단 (Judgement) |

### 아키텍처 규칙
- **출처 스푸핑 방지**: 요청 본문(JSON)에 `origin` 필드를 두지 않으며, 컨트롤러가 자신이 인입된 URL 경로를 기준으로 출처를 결정합니다. 적재 토큰을 가진 기체가 스스로를 "운영자 선언"으로 허위 승격할 수 없습니다.
- **등록 상태 머신 분리**:
  - `CLAIMED`: 운영자가 수동 선언했으나 아직 실제 통신이 확인되지 않은 상태
  - `DISCOVERED`: 어댑터가 플릿에서 탐지했으나 계약 계층 생존이 미확인된 상태
  - `CONFIRMED`: 기체로부터 실제 하트비트 생존 보고가 인입된 정상 가동 상태
  - `UNREGISTERED`: 공식 등록 엔드포인트를 거치지 않고 DB에 직주입된 상태

---

## 3. 어댑터 인스턴스 엔티티 도입 (§15.105)

기체 연결 설정의 위치를 정규화하기 위해 `adapter_instance` 테이블(V14 마이그레이션)을 도입하였습니다:
- **직결 기체**: 기체 자체가 네트워크 주소를 가지므로 `robot.endpoint`에 바인딩
- **플릿 기체**: 플릿 매니저의 접속 주소를 `adapter_instance`가 소유하고, 발견된 개별 기체는 `robot.discovered_by`로 인스턴스를 역참조

---

## 4. 검증 결과

`adapter-boston-dynamics-orbit` 모듈이 실제 플릿 발견 파이프라인을 구현하였으며, `OrbitDiscoveryEndToEndTest`를 통해 모의 플릿 서버로부터 기체가 자동 탐지되어 레지스트리에 `DISCOVERED` 상태로 등록되는 전 과정을 실증 검증하였습니다.
