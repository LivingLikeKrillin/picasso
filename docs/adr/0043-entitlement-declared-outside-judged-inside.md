# ADR 43 — 자동 승인 자격은 밖에서 선언되고 안에서 판정된다

- **설계 문서 참조**: §7 (자원 소유 대장), §15.165, ADR 9, ADR 41
- **결정 일자**: 2026-09-18
- **상태**: 결정됨 (규약 확정. 구현체는 소비자 확보 시점에 도입, ADR 9)

---

## 1. 맥락 및 배경

조치를 사람 대신 승인하는 권한을 자동 승인 자격이라 합니다. 해당 자격은 조치 유형 단위로 범위(셀·기종·스킬)와 만료를 붙여 사람이 선언하며, 런타임은 선언 목록에 존재하는지만 확인합니다. 계산된 자격은 계산이 틀리면 조용히 넓어지나, 선언된 자격은 사람의 행위이므로 감사 가능하고 만료를 걸 수 있습니다.

그 선언 목록이 어디에 있어야 하는가가 미결이었습니다. 설계 문서가 한쪽 절에서는 설정 파일로, 다른 절에서는 `registry` 로 서로 다르게 기재했으며, 양쪽 모두 아직 존재하지 않으므로 어느 쪽도 선례가 아닙니다.

실측 결과는 다음과 같습니다.

- `picasso` 모듈의 프로젝트 의존은 `contracts` · `capability` · `client` 셋뿐이며 `src/main` 에 `registry` 문자열이 0건입니다. 이는 누락이 아니라 모듈 정의에 명시된 성질입니다
- `picasso` 모듈은 `profile/` 을 직접 읽지 않습니다. 프로파일의 사실은 포트를 통해 들어옵니다
- 실재하는 선례는 생성자 인자입니다. `withholdEvery` 가 그 형태이며, 결속 정본·비용 함수·재할당 정책·바닥 소유 대장·작업 구역이 모두 동일한 형태로 주입됩니다

---

## 2. 핵심 결정 사항

**"자격 선언은 생성자 주입 포트로 들어오고, 판정은 승인 API 안에서 수행한다."**

- **위치는 포트입니다.** 설정 파일과 `registry` 는 그 포트의 구현체이며 위치가 아닙니다. 어느 쪽을 선택해도 본 계층의 코드는 동일하므로, 그 선택은 미결이 아니라 배치의 결정입니다
- **프로파일에는 두지 않습니다.** 프로파일은 기종의 사실이고 자동 승인 허용은 현장 정책입니다. 성질이 다른 두 값을 한 문서에 두면 기종 교체가 정책 변경을 동반합니다
- **판정은 본 계층이 수행합니다.** 호출자 신원을 승인 API 가 인자로 받아 선언 목록과 대조합니다. 호출하는 측이 자격을 스스로 판단하면 그 시점에 우회가 성립합니다
- **계약에는 올리지 않습니다.** 승인 API 는 계약 밖의 미들웨어 표면입니다. 호출자 신원을 계약에 올리면 어댑터 계약이 운영 주체를 알게 되며, 기종 중립성이 무너집니다
- **포트가 답하는 것은 선언뿐입니다.** 조치 유형·범위·만료까지이며 반복 카운터는 포함하지 않습니다

---

## 3. 결정 근거

1. **모듈의 성격을 뒤집지 않습니다.** 의존이 계약과 계약 소비자뿐이라는 것은 본 모듈의 정의된 성질이며, `registry` 의존을 추가하면 레지스트리 정지가 승인 정지로 전파됩니다. 실행 보증 계층의 가용성이 원장 계층의 가용성에 종속됩니다.
2. **정책은 데이터로 밖에, 판정은 코드로 안에 둡니다.** ADR 41 이 배정 정책에 내린 것과 동일한 형태입니다. 자격 목록을 바꾸면 누가 승인할 수 있는지가 바뀌고, 판정 규칙은 그대로입니다.
3. **선례가 하나뿐입니다.** 본 저장소에서 배치가 주는 값이 들어온 경로는 생성자 인자 하나이며, 기본값을 두지 않고 배치가 명시하는 형태입니다. 여섯 번째 값에 일곱 번째 경로를 만들 근거가 없습니다.
4. **배치의 결정을 코드가 대신하지 않습니다.** 설정 파일과 `registry` 중 무엇이 맞는지는 현장의 운영 체계가 답할 질문이며, 본 계층이 한쪽을 선택해 넣으면 다른 쪽을 고른 현장이 코드를 고쳐야 합니다.
5. **반복 카운터를 포트에 포함하지 않는 이유**: 반복 횟수는 본 계층이 이미 집계합니다(`Middleware.repeatedRemedies`). 밖에 질의하면 동일 수치의 원천이 둘이 되고, 두 값이 갈릴 때 반복 한도가 어느 쪽 값으로 걸리는지 판정할 수 없습니다.

---

## 4. 반복 카운터와 이의율의 비대칭

승인자 종류(사람·에이전트)를 두 지표에 반영하는 방식은 서로 반대입니다.

| 지표 | 승인자 종류별 분리 | 근거 |
|---|---|---|
| 반복 카운터 | **분리하지 않음** | 재는 대상이 **자원의 상태**입니다. 동일 조치가 몇 회 반복되었는가는 근본 원인의 지표이며, 근본 원인은 승인 주체를 구분하지 않습니다. 분리할 경우 사람 5회와 에이전트 5회가 10 이 아닌 5 와 5 로 집계되어 반복 한도에 도달하지 않습니다 |
| 이의율 | **분리함** | 재는 대상이 **판단 주체의 성능**입니다. 자동 진단이 맞는가를 재며 에이전트 승인이 그 검증 대상이므로, 사람 승인과 같은 통에 담으면 희석됩니다 |

**지표를 분리할지는 재는 대상이 자원인지 주체인지로 갈립니다.** 한쪽 규칙을 다른 쪽에 적용하면 두 지표 모두 목적을 잃습니다.

## 5. 대안 검토

| 대안 | 배제 사유 |
|---|---|
| 선언 목록을 `registry` 에서 직접 조회 | 모듈 의존이 증가하며 레지스트리 정지가 승인 정지로 전파됨. 해당 의존의 부재는 모듈의 선언된 성질임 |
| 선언 목록의 파일 경로를 주입 | 파일이라는 형태가 코드에 고정됨. 본 계층은 `profile/` 조차 직접 읽지 않음 |
| 프로파일에 자격을 기재 | 기종의 사실과 현장 정책이 한 문서에 혼재하며, 기종 교체가 정책 변경을 동반함 |
| 호출하는 측이 자격을 판단 | 판단 주체가 곧 우회 경로가 됨. 자격 판정이 승인 API 에 있어야 한다는 불변식이 성립하지 않음 |
| 호출자 신원을 계약에 추가 | 승인은 계약 밖의 표면이며, 어댑터 계약이 운영 주체를 알 이유가 없음(ADR 36) |
| 반복 카운터를 승인자 종류별로 분리 | 동일 우회가 두 통으로 나뉘어 반복 한도에 도달하지 않음. 지표가 자체 집계 방식에 의해 무력화됨 |
