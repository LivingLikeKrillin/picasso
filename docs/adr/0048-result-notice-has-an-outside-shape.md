# ADR 48 — 작업 응답에 바깥 형식을 두고, 승인 응답과 실행 · 단위 · 인스턴스로 잇는다

- 상태: 확정 (2026-10-02)
- 관련: [ADR 46](0046-consumed-approval-is-recorded.md) 승인 소모 기록 · [ADR 44](0044-approval-names-a-proposal-not-an-action.md) 승인은 제안을 가리킨다 · [ADR 9](0009-no-declaration-without-consumer.md) 소비자 존재 원칙 · [ADR 36](0036-work-first-assignment-vs-execution.md) 작업 배정 어휘와 실행 계약 어휘의 계층 분리
- 변경 이력: 설계 문서 §15.203

## 맥락

바깥 루프(koshei)는 picasso 의 소비자다. 승인 창구로 조치를 승인하고, 작업 응답(`JobResponse`)를 그 조치의 완료 근거로 쓴다. 판정은 이렇다. 승인 응답의 `executionId` 로 작업 응답을 잇고, 의심(`inDoubtUnits` · `unverifiedUnits` 가 비지 않거나 `operatorRequired`)이면 모름이며, 대상 단위가 `completedUnits` 에 있으면 끝났다.

이 판정이 결과 통보만으로는 끝에 닿지 못했다. 막는 것이 넷이었다.

- **작업 응답에 실행이 없었다.** 지시(`jobOrderId`)만 가리켰고, 소비자는 지시 → 실행 대응표를 따로 들어야 했다. 같은 지시가 다시 서면 그 표가 틀린다.
- **승인된 단계가 어느 단위인지 몰랐다.** 조치 단위의 이름 `remedy-{n}-{skillType}` 은 구현이 그렇게 지었을 뿐 규약이 아니었다.
- **시도를 가를 것이 없었다.** `exec-N` · `resp-N` 은 인스턴스 안의 셈이라 다시 뜨면 되풀이되고, 작업 응답의 `version` 은 지시의 버전이다.
- **작업 응답을 밖으로 내는 형식이 없었다.** 프로세스 안의 `pending()` · `responses()` · `ack()` 뿐이었다. 소비자는 picasso 를 품지 않는다 — 에이전트 계층이 죽을 때 실행 보장까지 같이 죽기 때문이다. 작업 응답을 나르는 것은 picasso 를 세우는 담는 쪽이고, 소비자는 그 바깥 형식을 프로세스 밖에서 읽는다.

소비자가 실제로 물었다(바깥 루프 세션, 2026-10-02).

## 결정

**인스턴스 식별자를 둔다.** `Middleware.instanceId` 는 미들웨어가 뜬 한 번을 가리키는 값이고, 기본은 무작위다. 승인 응답과 작업 응답의 바깥 형식이 같은 값을 싣는다. (`instanceId`, `executionId`) 짝이 다시 뜬 뒤에도 한 시도를 가리킨다. 결정적으로 짓지 않는다 — 같은 시드로 다시 띄운 인스턴스가 같은 값을 내면 앞 구동의 통보가 이번 시도의 것으로 읽힌다. 이름을 `runId` 로 하지 않은 것은 대장 내보내기의 런 식별자가 이미 그 이름을 쓰기 때문이다.

**작업 응답이 실행을 가리킨다.** `JobResponse.executionId` 를 둔다. 통보를 짓는 자리(`notify`)가 실행을 쥐고 있으므로 picasso 가 찍는다. 담는 쪽이 대응표로 덧붙이면 담는 쪽마다 그 표가 갈린다.

**작업 응답에 바깥 형식을 둔다(버전 1).** `ResultExport` 는 순수 함수다 — 문자열만 짓고 파일도 소켓도 건드리지 않는다(§6 의 `LedgerExport` 와 같은 자리). 한 줄이 작업 응답 하나이며, 줄마다 `schemaVersion` 과 `instanceId` 를 싣는다. 담는 쪽은 줄 단위로 나르므로 안내 파일이 버전을 들 자리가 담는 쪽마다 다르다. 칸은 작업 응답의 이름 그대로이고, 빈 목록도 키를 빼지 않는다. 상위 확인 상태(`ack`)는 싣지 않는다 — 나르는 쪽의 상태이고, 실으면 같은 통보가 확인 전후로 두 모양이 된다. 파일 이름(`job-responses.jsonl`)은 준다. 어디에 어떤 주기로 쓸지, 안내 파일을 둘지는 담는 쪽이 정한다.

**승인 창구 규약의 버전을 3 에서 4 로 올린다.** 모든 응답에 `instanceId` 를, APPROVED 의 단계와 소모 기록의 단계마다 `unitId` 를 싣는다. 조치 시퀀스는 실행 계획의 맨 앞에 단계 순서대로 서고, 단위 이름은 `remedy-{n}-{skillType}`(n 은 1부터)이다. 이것이 이제 규약이다. 칸이 느는 것뿐이지만 버전을 올린다 — 작업 응답과 잇는 칸이라, 읽는 쪽이 버전을 보고서야 이 칸으로 묻는다.

**참조 한 세트를 쓴다.** 승인 창구 구동기(§7.5)가 두 대장과 같은 자리에 `job-responses.jsonl` 을 쓴다. 담는 쪽의 참조일 뿐 실물 담는 쪽이 아니다 — 상위 확인을 하지 않으므로 같은 통보가 매번 다시 실린다. 대장 한 세트의 안내는 이 파일을 세지 않는다. 버전도 소유자도 다르다.

## 왜 이 모양인가

**쓰기는 담는 쪽이다.** picasso 가 파일 쓰기까지 들면 담는 쪽의 결정(어디에 · 어떤 주기로 · 안내 파일을 둘지)을 먼저 정해 버린다. 대장 내보내기와 같은 가름이며, 담는 쪽이 바뀌어도 이 형식은 그대로다.

**`instanceId` 와 `unitId` 는 picasso 만 실을 수 있다.** 승인 응답은 picasso 가 짓는다. 담는 쪽이 대신 붙일 길이 없으므로 형식을 담는 쪽에 맡기면 승인 응답 쪽이 비고, 형식이 담는 쪽마다 갈린다.

**`version` 의 뜻을 바꾸지 않는다.** 작업 응답의 `version` 은 ISA-95 응답의 대응 칸이다(`docs/isa95.md` §2). 시도를 가르는 데 빌려 쓰면 표준 대응이 깨진다. 시도는 따로 둔 (`instanceId`, `executionId`) 가 가른다.

**`executionId` 는 자체 확장이다.** 작업 응답은 작업 배정 쪽 어휘(ISA-95)의 모양이고 실행은 이 계층의 어휘다(ADR 36). 표준 응답은 지시를 가리키지만, 승인으로 선 실행을 받은 쪽은 실행으로 잇는다. 같은 지시의 두 실행을 가를 길이 표준 칸에는 없다.

## 고르지 않은 것

**picasso 가 적재기까지 내기.** 위와 같다.

**형식은 담는 쪽이 정하고 picasso 는 칸만 더하기.** 승인 응답의 `instanceId` · `unitId` 는 picasso 만 실을 수 있고, 형식이 담는 쪽마다 갈린다.

**단계 단위를 규약 없이 이름 규칙으로 두기.** 읽는 쪽이 이름을 추측해 잇게 된다. 이름을 바꾸는 사람은 그 추측을 모른다.

**작업 응답을 승인 창구로 조회하기.** 루프백 조회 표면은 새 읽기 경로이고 §6 의 실시간 조회 승격 조건에 걸린다. 나르는 쪽이 이미 있는 자리(담는 쪽)를 두고 표면을 하나 더 열 이유가 없다.

## 대가

**실물 담는 쪽이 없다**(§15.203). 형식은 섰지만 그것을 나르는 배치 호스트는 사용자 결정으로 남아 있다. 그때까지 소비자가 실물로 받는 것은 구동기의 참조 한 벌뿐이다.

**버전이 올라 읽는 쪽이 따라와야 한다.** 승인 창구 버전 4 를 모르는 읽는 쪽은 응답을 «못 읽음» 으로 막을 수 있다. 버전 3 때 실제로 그럴 뻔했다. 머지 전에 두 소비자에게 해시와 함께 알린다.

**`instanceId` 는 인증이 아니다.** 응답을 낸 인스턴스를 가리킬 뿐이고, 창구는 루프백 전용이며 신원을 인증하지 않는다(§15.3).
