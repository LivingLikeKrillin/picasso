# ADR 52 — 셀 안전 상태를 정보로 비춘 작업 허가로 새 발행과 재개를 막는다

- 상태: 확정 (2026-10-14)
- 관련: [ADR 9](0009-no-declaration-without-consumer.md) 소비자 존재 원칙, [ADR 32](0032-safety-boundary.md), [ADR 36](0036-work-first-assignment-vs-execution.md), [ADR 42](0042-no-command-without-an-owner.md), [ADR 51](0051-three-authority-boundaries.md)
- 변경 이력: 설계 문서 §15.219

## 맥락

이 결정은 설계 문서 D 단계인 재할당과 안전 상태 연계 검토(«셀 단위 안전 상태를 반영한 작업 허가와 재개»)에서 도출되었고 2026-10-13 소유자가 결정했다.
ADR 32는 비상정지, 보호 정지, 사람 감지를 계약 위로 올리지 않는다.
그동안 picasso Core와 picasso-ops에는 작업 허가, 안전 상태, 셀 보류 개념이 없었다.
picasso-ops는 신호마다 읽기 전용인 `safety` 불리언을 갖지만 스테이션 조정은 그 신호를 쓰지 않았다.
ADR 51 결정 6은 발행 관문 하나에 입력 둘(유효 권위, 작업 허가)을 정했고 작업 허가를 앞으로 올 둘째 입력으로 남겼다.

## 결정

**결정 1. 작업 허가는 안전 계통의 상태를 기체 집합마다 비춘 정보 투영이며 picasso의 안전 기능이 아니다.** 비상정지, 보호 정지, 사람 감지는 계약 아래 안전 계통의 것이며 picasso 기능이 아니다(ADR 32). 작업 허가(Work Permit)는 안전 계통 상태를 기체 집합마다 비춘 정보 투영이다. picasso는 작업 허가 값으로 새 로봇 명령만 내지 않는다. 이미 발행된 명령은 세우지 않는다. 발행 관문(Issuing Gate)이 열려도 안전 계통이 막으면 기체는 멈춘다. 관문이 닫혀도 안전 계통의 정지가 아니면 이미 나간 명령은 멈추지 않는다(`IssuingGate`, `WorkPermitPort`).

**결정 2. 작업 허가는 계약 밖 포트로 읽으며 계약 proto를 변경하지 않는다.** `WorkPermitPort.read(): List<PermitReading>`으로 판독값을 가져온다. `PERMITTED`, `INHIBITED`, `UNKNOWN` 어휘(`WorkPermit`)는 picasso 저장소의 것이며 proto에 들어가지 않는다. ADR 9에 따라 소비자는 발행 관문 하나뿐이다. ADR 36에 따라 로봇 케이퍼빌리티 표면에는 해당 어휘가 없다. 게이트의 `DocumentClaimsTest`에서 `작업 허가 어휘가 계약 proto 로 안 샌다` 시험으로 이를 집행한다.

**결정 3. 작업 허가 범위의 열쇠는 기체 식별자 집합이다.** `PermitScope.robots`는 `Set<String>?` 타입을 쓴다. 구역이나 셀 객체를 범위 열쇠로 쓰지 않는다. 구역을 기체 목록으로 해석하는 책임은 현장의 허가 원천에 둔다.

**결정 4. 발행 관문 하나에 유효 권위와 작업 허가를 순서대로 검사하며 검사 위치는 셋이다.** `IssuingGate.check(robots)`는 첫째 입력인 유효 권위를 먼저 보고 둘째 입력인 작업 허가를 본다. 단일 활성이므로 현재 유효 권위 거부(`authorityRefusal`)는 늘 null이다. 리스와 세대는 구현하지 않는다(ADR 51 결정 3). 검사 위치는 `pumpRound`의 `startUnit` 앞(로봇 경로), `revise`의 `robots.start` 앞(수행 중인 로봇 단위의 갱신), `resolveDoubt`의 조회 앞(로봇 경로)이다. 미확정 조회가 동일 참조의 `StartTask` 재전송이라 원 요청이 닿지 않았으면 새 접수가 되기 때문에 관문에 건다. 이는 ADR 51 결정 6이 명시한 둘 밖의 셋째 자리다. 이 결정은 ADR 51 결정 6의 뜻을 새 로봇 명령이 나가는 자리 전부로 넓혀 적용한다.

**결정 5. 작업 허가는 새 로봇 명령의 발행만 막고 취소, 관측, 스냅숏, 재생은 검사하지 않는다.** 수행 중인 단위의 취소는 `INHIBITED` 상태여도 기체로 전달된다. 실행은 중단으로 종료된다. 발행 전에 막힌 실행의 취소도 허가를 기다리지 않고 즉시 종료된다.

**결정 6. UNKNOWN 상태는 닫힌 쪽으로 해석하여 막고 범위를 모르면 원천이 맡은 전체 기체를 막는다.** 원천 보고(`REPORTED`), 유효 기간 만료(`EXPIRED`, `observedAt + validFor`), 원천 세션 변경(`SESSION_CHANGED`, 줄의 세션과 판독 세션 불일치), 대상 기체 불명(`SCOPE_UNKNOWN`), 미적용 기체(`NOT_COVERED`), 포트 예외 발생(`PORT_FAILED`)의 여섯 가지 `PermitCause`로 `UNKNOWN`이 결정된다. `PermitScope.robots`가 null이면 `PermitReading.governed` 전부를 `UNKNOWN`으로 처리한다. 마지막으로 확인한 범위만 막지 않는다. 허가 원천이 해당 줄에 `PERMITTED`라고 보고했어도 전체를 막는다.

**결정 7. 결함 관문과 허가 관문의 침묵 거동을 서로 다르게 분리한다.** 결함 관문(`blockingFaults`)은 결함을 묻지 못해도 관측 실패로 현장을 세우지 않기 위해 통과시킨다. 반면 발행 관문의 작업 허가는 안전 상태의 정보 투영이므로 상태를 모르면 막는다.

**결정 8. 허가로 막힌 단위는 실패가 아니라 대기 상태로 두고 막힘 정보를 실행과 자취에 명시적으로 드러낸다.** 허가 막음이 걸린 단위는 `PENDING` 상태를 유지한다. 실행 상태를 운영자 보류로 바꾸지 않는다. 인시던트를 열지 않으며 작업 응답(`JobResponse`)도 내지 않는다. 작업 허가가 `PERMITTED`로 돌아오는 라운드에 명령을 내보낸다. `Execution.permitBlock`에 대상 단위, 막힌 명령 종류(`WithheldIssue`: `START`, `REVISION_UPDATE`, `IN_DOUBT_LOOKUP`), 기체별 `RobotPermit`(값과 `PermitReason`: 원천, 까닭, 막는 주체, 풀릴 근거, 관측 시각), 최초 막힘 시각을 기록한다. 실행 자취에는 `ISSUE_WITHHELD`와 `ISSUE_RESUMED`를 남긴다. 동일한 막힘은 관측 시각을 식별 키에서 제외하여 한 번만 기록한다.

**결정 9. 운영자 해제는 결함 막음만 감수하며 허가 막음은 풀지 못한다.** `permitBlock`은 결함 막음 필드인 `blockedBy`와 구분되는 독립된 칸이다. 운영자 `release` 명령은 결함만 감수한다. 결함 막음과 허가 막음이 함께 걸려 있을 때 운영자가 해제하더라도 결함만 감수되고 작업 허가가 `PERMITTED`로 돌아와야 명령이 나간다.

**결정 10. 허가 포트를 주입하지 않은 환경은 기존 발행 동작을 그대로 유지한다.** `Middleware(permits = null)`을 기본값으로 둔다. 허가 원천을 붙이지 않은 현장까지 닫으면 원천이 없는 현장이 통째로 멈추기 때문이다. 닫힌 쪽 거동은 포트를 명시적으로 주입한 뒤부터 적용된다. 기존 picasso 시험 411개는 변경 없이 통과한다.

**결정 11. 개정 명령이 막히면 리비전과 기대는 새 버전으로 반영하고 기체 전송만 미룬다.** `Execution.deferredUpdate`에 미룬 전송을 둔다. 전송이 미뤄진 사이 이전 버전으로 단위가 끝나면 새 버전 기대를 기준으로 설비 확인 경로를 거친다. 끝내 보내지 못한 갱신은 실행 자취에 남긴다. 막힌 상태에서 버전이 다시 오르면 기체에서 수행 중인 첫 버전을 유지한다. 작업 허가가 돌아왔을 때 마지막 버전 하나에 미룬 갱신을 한 번에 실어 보낸다.

## 왜 이 모양인가

비상정지, 보호 정지, 사람 감지는 계약 아래 안전 계통의 고유 책임이다. picasso는 안전 계통을 대신하지 않으며 그 상태를 정보 투영으로 읽어 새 명령을 내지 않는 역할만 맡는다. 관문이 열려 있어도 안전 계통이 기체를 세우며, 관문이 닫혀도 안전 계통의 개입이 없으면 이미 발행된 명령은 기체에서 계속 진행된다.
작업 허가 어휘는 소비자인 발행 관문 하나에서만 쓰인다. 로봇 케이퍼빌리티 표면에는 허가 개념이 존재하지 않으므로 계약 proto를 수정하지 않고 계약 밖 포트로 분리했다.
구역이나 셀 객체를 picasso 내부에 모델링하면 현장의 공간 정의를 소프트웨어가 직접 해석해야 하는 부담이 생긴다. 구역을 기체 목록으로 풀어내는 책임을 현장 허가 원천에 맡기고 picasso는 기체 식별자 집합만 확인한다.
작업 허가는 안전 상태를 비추는 정보이므로 모호한 상태를 열어 둘 수 없다. 만료, 세션 불일치, 원천 미지정, 예외 등으로 상태를 알 수 없으면 닫힌 쪽인 `UNKNOWN`으로 취급하여 명령 발행을 차단한다. 대상 범위를 알 수 없을 때도 마지막으로 관측된 범위에 기대지 않고 원천이 맡은 전체 기체를 막아 누락을 방지한다.
결함 관문은 관측 실패 때문에 전체 현장이 멈추는 것을 막기 위해 기존부터 통과 거동을 취해 왔다. 이 두 침묵은 목적이 다르므로 서로 다른 규칙으로 처리한다.
허가 막음은 시스템 결함이나 임무 실패가 아니다. 작업 지시를 거부하거나 실패로 종결하지 않고 `PENDING` 상태로 대기시킴으로써 현장의 안전 상태가 복구되었을 때 지체 없이 명령을 재개한다.
허가 포트를 연결하지 않은 현장은 기존 동작을 그대로 보장하여 허가 원천이 없는 현장의 서비스 중단을 방지한다.

## 고르지 않은 것

첫째, 허가 어휘를 계약 proto에 올리는 방안을 고르지 않았다. ADR 9에 따라 소비자는 발행 관문 하나뿐이며 ADR 36에 따라 로봇 케이퍼빌리티 표면에는 허가 어휘가 없기 때문이다.
둘째, 구역과 작업 공간 객체를 범위 열쇠로 쓰는 방안을 고르지 않았다. 구역을 기체 집합으로 푸는 책임은 허가 원천의 몫이다.
셋째, 영향 범위를 모를 때 마지막으로 확인한 범위만 막는 방안을 고르지 않았다. 새로 추가된 대상을 놓칠 위험이 있기 때문이다.
넷째, 포트를 붙이지 않은 현장까지 닫는 방안을 고르지 않았다. 원천이 없는 현장이 통째로 멈추고 관문이 곧바로 무력화되기 때문이다.
다섯째, 막힌 단위를 실패로 접거나 운영자 보류로 바꾸는 방안을 고르지 않았다. 불필요하게 실패를 확정하거나 인시던트를 열 이유가 없다.

## 대가

네 가지 한계가 한계 레지스터 §15.219의 행으로 남는다.
첫째, 미확정 단위의 취소가 작업 허가가 돌아올 때까지 하위 계통으로 나가지 않는다.
둘째, 허가 막음 정보가 작업 응답이나 내보내기에 실리지 않는다.
셋째, 플릿 경로 위임은 발행 관문을 거치지 않는다.
넷째, 다시 짓기 뒤의 재부착도 관문에 의해 막힌다.
추가로 다음 세 가지 운영 및 구현 비용이 발생한다.
포트를 붙였는데 어느 허가 원천도 덮지 않는 기체는 막히므로 원천은 모든 기체를 `governed` 목록에 빠짐없이 넣어야 한다.
세션 변경은 줄마다 단일 세션 태그로만 판정하므로 허가 원천이 태그를 정직하게 부여한다는 전제가 필요하다.
포트는 검사하는 자리마다 새로 읽으므로 `WorkPermitPort.read`는 호출을 지연시키지 않는 스냅숏이어야 한다.

## 다른 결정과의 관계

ADR 32와의 관계: 이 결정은 ADR 32를 보완하며 대체하지 않는다. 안전 기능은 계약 아래에 머문다. 검증기(`MissionValidator`)가 안전 신호를 기다리는 설비 대기를 거부하는 규칙은 그대로 유지된다. 작업 허가는 대기 노드가 아니며 임무 정의에 안전 신호를 넣지 않는다.
ADR 42와의 관계: ADR 42의 "소유자 미확정이면 명령 금지" 규칙과 짝을 이룬다. 허가 상태를 모르면 새 명령을 금지한다.
ADR 51과의 관계: ADR 51 결정 6에서 정의한 발행 관문의 "앞으로 올 둘째 입력"을 구현한다. 첫째 입력인 유효 권위는 현재 자리만 둔다. 미확정 조회 위치를 관문에 연결한 것은 ADR 51 결정 6이 언급한 `startUnit`과 `revise` 외의 셋째 자리다. 이 결정은 ADR 51 결정 6의 뜻을 새 로봇 명령이 나가는 자리 전부로 해석한다.
ADR 9 및 ADR 36과의 관계: 소비자가 발행 관문 하나뿐이며 로봇 표면에 허가 어휘가 없다는 점은 작업 허가 포트가 계약 밖으로 분리되고 proto가 변경되지 않는 근거가 된다.
