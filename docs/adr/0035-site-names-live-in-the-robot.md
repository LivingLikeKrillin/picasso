# ADR 35 — 사이트 명칭 및 지리 공간 정보의 기체 내부 저장 원칙

- **설계 문서 참조**: §4.3 (값 어휘 체계), §9.7 ④, §15.68, ADR 34
- **결정 일자**: 2026-09-08
- **상태**: 결정됨 (코드베이스 반영 완료)

---

## 1. 맥락 및 배경

인터페이스 계약의 주요 파라미터는 현장 사이트 수준의 의미론적 명칭(`location`, `destination`, `target`, `object_id`)을 사용합니다. ADR 34에서 "어댑터는 매핑 테이블을 소유하지 않는다"고 결정하였으나, 해당 매핑 정보를 저장하고 해석할 최종 주체는 확정되지 않았습니다.

이와 관련하여 두 가지 핵심 질문이 제기되었습니다:
1. **위치 좌표의 지식 소유권 (Who knows)**: 특정 설비(예: `dock-3`)의 물리적 위치는 사이트(공장/창고) 엔지니어링 주체만이 알고 있습니다.
2. **로봇으로의 전파 메커니즘 (How to deliver)**: 사이트의 명칭 지식이 로봇 제어기로 전달되는 경로가 어떻게 구성되는가의 문제입니다.

소비자가 기종별로 상이한 좌표나 내부 ID를 직접 관리해야 한다면 "단일 클라이언트 코드로 이종 로봇 제어"라는 원칙(A-1)이 파괴됩니다.

---

## 2. 핵심 결정 사항

**"인터페이스 계약은 현장 표준 사이트 명칭을 전달하며, 해당 명칭의 좌표 결속은 사이트 커미셔닝 시점에 기체 내부 세계 모델에 사전 등록된다."**

- **어댑터의 비소유 원칙**: 어댑터는 정적 매핑 사전을 보유하지 않으며, 로봇 제어기에 질의하여 동적으로 변환하거나 벤더 쿼리 구조체로 직렬화하여 전달합니다.
  - Spot: `Waypoint.id`는 로봇 내부 생성 고유 ID이므로, 어댑터는 매 호출 시 `DownloadGraph`를 조회하여 인간이 부여한 `Waypoint.Annotations.name`과 일치하는 ID를 동적으로 획득합니다.
  - Digit: `destination` 명칭을 `ObjectSelector{name}` 쿼리로 직접 투망하여 기체 내부 세계 모델이 런타임에 대상을 해석하도록 위임합니다.
- **사전 커미셔닝 분리**: 지리 정보 및 설비 명칭 등록은 런타임 RPC가 아닌 배포 사전 작업(Offline Setup)으로 수행됩니다 (Spot의 지도 녹화 및 웨이포인트 주석 부여, Digit의 `add-object`/`add-landmarks`).
- **레지스트리의 상태 관리 (`conformance_status`)**: `registry` 서비스는 명칭-좌표 매핑 데이터 자체를 보관하지 않으며, 해당 기체가 사이트 명칭 집합을 정상 인지하고 있는지 여부(등록 상태 메타데이터)만을 관리합니다.

---

## 3. 결정 근거

1. **클라이언트 코드의 기종 독립성 보장 (A-1)**: 클라이언트는 기종과 무관하게 항상 일관된 비즈니스 명칭(`dock-3` 등)으로 명령을 하달할 수 있습니다.
2. **벤더 표준 프랙티스와의 정합성**: Boston Dynamics(GraphNav) 및 Agility Robotics(World Model) 모두 기체 내부에 인간 친화적 명칭을 앵커링하는 메커니즘을 자체 제공하고 있습니다.
3. **레지스트리 결합도 격리 (§3.2)**: 레지스트리가 좌표 사전을 소유하고 기체에 강제 푸시하는 구조를 배제함으로써 서비스 간 결합도를 최소화합니다.

---

## 4. 런타임 질의 체계 및 어휘 세분화

계약에 `SkillService.GetKnownSiteNames` RPC가 정의되어 기체가 지원하는 명칭 집합을 직접 질의할 수 있습니다. 어댑터는 기체의 응답 능력에 따라 다음 3가지 도메인 상태로 응답합니다:
- `Known`: 기체 세계 모델에서 명칭 목록 정상 반환
- `Unsupported`: 기체 제어기가 세계 모델을 미지원 (Unitree G1 등)
- `Unavailable`: 통신 일시 장애 등으로 인한 조회 불가

질의 실패를 단순 빈 목록(0건)으로 처리하지 않고 상태를 분리함으로써 시스템 관측성을 확보합니다 (§15.73).
