# ADR 46 — 승인 소모를 기록하고 CONSUMED 로 가른다

- 상태: 확정 (2026-10-01)
- 관련: [ADR 44](0044-approval-names-a-proposal-not-an-action.md) 승인은 제안을 가리킨다 · [ADR 45](0045-revocation-is-marked-not-deleted.md) 철회는 지우지 않고 표시한다 · [ADR 9](0009-no-declaration-without-consumer.md) 소비자 존재 원칙
- 일지: 설계 문서 §15.201

## 맥락

같은 (기체, 주문)에 승인이 두 번 오면 둘째는 `NO_PROPOSAL` 이다. 제안은 승인이 접수로 이어진 뒤에 한 번 지워지고(`RemedyDesk.settle`), 승인 창구는 구동 루프와 같은 자물쇠를 지난다. 그래서 **같은 제안이 두 번 나가는 일은 이미 없다.**

모자란 것은 **부르는 쪽이 아는 길**이다. 바깥 루프는 최소 한 번 실행되는 실행 단위에서 승인을 보낸다. 요청 직후 응답을 받기 전에 죽으면, 다시 뜬 쪽은 자기 요청이 들어갔는지 모른다. 그때 받는 `NO_PROPOSAL` 은 세 경우를 접는다.

| 경우 | 다음 행동 |
|---|---|
| 내 앞선 요청이 소모했다 | 실행의 근거(결과 통보)를 기다린다 |
| 다른 승인자가 소모했다 | 누가 무엇을 보냈는지 확인한다 |
| 처음부터 제안이 없었다 | 탐색 대장에서 그 (기체, 주문)의 답을 읽는다 |

`orchestration.md` §7.3 이 거절 종류를 가르는 기준은 **후속 조치가 다르면 가른다**이고, 앞의 둘과 셋째는 후속 조치가 다르다. 그리고 §7.3 표가 `NO_PROPOSAL` 에 적어 둔 후속 조치 «다시 읽고 다시 시도» 는 세 경우 어디에도 맞지 않는다. 다시 시도하면 셋 다 다시 `NO_PROPOSAL` 이다.

소비자가 실제로 물었다. 설명 층이 바깥 루프의 설계를 대조하다 이 접힘을 짚었다(자문 2026-09-27, 답 2026-09-30).

## 결정

**소모를 기록한다.** 승인이 접수로 이어져 제안을 지울 때(`settle`) (기체, 주문)마다 소모 기록(`ConsumedApproval`) 하나를 남긴다. 기록은 다음을 든다.

| 칸 | 값 |
|---|---|
| 승인자 | id 와 종류(`PERSON` · `AGENT`) |
| `at` · `wallClockAt` | 소모한 순간의 가상 시각과 실 시각 |
| `executionId` | 그 승인으로 선 실행 |
| `steps` | 승인 답이 돌려준 `steps` 와 같은 것 — 걸음마다 조치 유형과 값 |

같은 열쇠가 다시 소모되면 덮어쓴다. 두 문(사람의 `approveRemedy`, 밖의 `attemptApproval`)이 같은 `settle` 을 지나므로 둘 다 기록된다. 이를 위해 `settle` 은 승인자와 `executionId` 를 받는다. 승인자는 판정(`Judgment.Go`)이 들고 오고, `executionId` 는 접수가 된 실행에서 `commit` 이 넘긴다.

**판정 순서에 한 자리를 더한다.**

1. 가림 → `WITHHELD`
2. 서 있는 제안이 없으면: 소모 기록이 있으면 `CONSUMED`, 없으면 `NO_PROPOSAL`
3. 서 있는 제안이면 지금 순서 그대로(`PROPOSAL_CHANGED` → 능력 → 자격 → 값)

소모 뒤 같은 열쇠에 새 제안이 서면 새 제안이 이긴다. 기록은 «지금 서 있는 것이 없을 때» 만 읽힌다.

**`CONSUMED` 와 기록은 짝으로만 선다.** 거절(`ApprovalOutcome.Refused`, 판정의 `Judgment.No`)은 소모 기록 칸을 하나 갖고, 만들 때 검사한다. `CONSUMED` 는 기록 없이 만들어지지 않고, 다른 거절은 기록을 들지 못한다. 안 그러면 인코더가 `"refusal":"CONSUMED","consumed":null` 을 낼 수 있고, 그것은 «소모됐지만 누가인지 모른다» 를 정상 답처럼 보인다.

**`CONSUMED` 는 하나의 값이다.** «내 요청» 과 «다른 승인자» 는 후속 조치가 다르지만 이 층은 어느 요청이 부르는 쪽의 것인지 모른다. 승인자 id 는 부르는 쪽의 주장이고(§15.3) 재시도마다 같다. 그래서 비교는 부르는 쪽이 기록의 승인자를 자기 id 와 대 보는 것으로 한다.

**승인 창구 규약의 판을 2 에서 3 으로 올린다.** 거절 답에 `consumed` 칸을 둔다. `CONSUMED` 면 기록이고, 다른 거절은 키를 빼지 않고 `null` 을 적는다. 승인 답(`APPROVED`)은 이 칸을 싣지 않는다. 시각은 ISO-8601 이다(§6 의 적재 규약과 같다).

```json
{"schemaVersion":"3","contractSemver":"0.9.0","outcome":"REFUSED","refusal":"CONSUMED",
 "reason":"이미 소모된 제안이다: narrator-1(AGENT) · exec-2",
 "consumed":{"approverId":"narrator-1","approverKind":"AGENT",
             "at":"2026-09-06T00:00:01Z","wallClockAt":"2026-10-01T07:12:44.120Z","executionId":"exec-2",
             "steps":[{"skillType":"pick_place","parameters":{"destination":"DROP-01","object_id":"ENGINE-COVER-A"}}]}}
```

칸 이름은 이미 있는 것을 쓴다. `approverId` · `approverKind` 는 승인 요청에서, `executionId` · `steps` 는 승인 답에서, `at` · `wallClockAt` 은 §6 의 적재 규약에서 왔다.

**`NO_PROPOSAL` 은 좁아진다.** 이제 «이 프로세스가 뜬 뒤로 그 (기체, 주문)에 제안이 선 적이 없다» 는 뜻이다. `orchestration.md` §7.3 표에서 `NO_PROPOSAL` 과 `PROPOSAL_CHANGED` 를 한 행에 둔 것을 가르고, `CONSUMED` 행을 더한다. 새 행의 후속 조치는 위 맥락 표의 것을 그대로 옮긴다.

## 왜 이 모양인가

**기록하는 자리가 `settle` 이다.** 소모는 제안이 지워지는 것이고, 제안을 지우는 곳은 접수가 된 뒤의 `settle` 하나뿐이다. `executionId` 도 접수가 된 뒤에만 생긴다. 관문 거절과 멱등 접힘은 `settle` 에 닿지 않으므로 제안이 지워지지 않고, 재시도는 `CONSUMED` 가 아니라 서 있는 제안의 판정을 받는다.

**덮어쓴다.** 한 열쇠에 서 있는 제안은 많아야 하나이고, 부르는 쪽이 묻는 것은 «지금 왜 없는가» 다. 앞선 소모의 이력은 이 층이 따로 들지 않는다 — 사건이 열린 실행이면 사건 번들의 `approvedBy` 가 승인자를 든다.

**전부 싣는다.** 부르는 쪽은 기록의 승인자가 자기 id 인지로 «내 요청» 을 가르고, 무엇이 나갔는지 알아야 다음 행동을 정한다. 승인 답이 실제로 실린 값을 돌려주는 것(ADR 44)과 같은 이유다.

**판을 올린다.** 칸이 느는 것만이면 모르는 칸을 무시하면 그만이지만, `refusal` 로 가르는 읽는 쪽은 모르는 값을 만난다. 판 2 에서 `REVOKED` 를 더할 때와 같은 이유다.

## 고르지 않은 것

**멱등 열쇠.** 요청에 열쇠를 싣고 같은 열쇠에 첫 결과를 돌려주면 «내 요청» 을 정확히 가른다. 그러나 요청 칸이 늘어 ADR 44 의 요청 모양을 고쳐야 하고, 열쇠 표가 상한 없이 자란다. 소모 기록으로 충분한 조건은 둘이다.

- 부르는 쪽이 한 (기체, 주문)에 한 승인자 id 로 한 번에 시도 하나만 한다.
- 첫 시도와 재시도 사이에 같은 열쇠에 **새 제안이 서지 않는다.** 서면 재시도는 그 새 제안으로 판정되어 `CONSUMED` 를 보지 못한다. 조치 유형 열이 다르면 `PROPOSAL_CHANGED` 를 받고, 같으면 그 새 제안을 승인까지 한다(`sawSkillTypes` 는 유형의 열만 대조한다).

v1 에서 둘째 창은 열리지 않는다. 실행은 지워지지 않으므로 소모된 주문의 재접수는 전부 개정(`revise`)으로 가고, 개정의 거절은 걸음이 있는 제안을 내지 못한다(§15.175). 창이 열리는 날은 **개정의 거절이 걸음 있는 제안을 낼 수 있게 되는 날**이다 — §15.175 가 도달 경로를 다시 보라고 적은, 파지를 바꾸는 스킬이 `pick_place` 말고도 생기는 날이다. 그날, 또는 첫째 조건이 안 서는 소비자가 오는 날 멱등 열쇠를 다시 본다(ADR 9). §15.175 를 고쳐 개정 경로가 조치 열을 받게 되면, 그때부터는 그 창에서의 재시도가 조치를 실제로 다시 내보낸다.

**별도 조회 표면.** (기체, 주문)으로 승인 결과를 묻는 읽기 경로는 새 표면이고, `orchestration.md` §6 의 실시간 조회 승격 조건에 걸린다.

**적재에 소모 싣기.** `CONSUMED` 는 창구를 부르는 쪽에만 닿는다. 파일 적재(`remedy-searches.jsonl`)는 소모된 열쇠에도 `FOUND` 줄을 그대로 싣는다 — 탐색 줄은 탐색의 답이지 제안 표가 아니다. 적재를 읽는 쪽이 소모를 알아야 한다는 요청은 아직 없다(ADR 9).

**소모의 이력.** 열쇠마다 마지막 하나면 «지금 왜 없는가» 에 답한다.

## 대가

**기록도 프로세스 수명과 같다**(§15.166). picasso 가 다시 뜨면 제안도 소모 기록도 사라지고, 소모됐던 열쇠의 재시도도 `NO_PROPOSAL` 을 받는다. 재시작을 넘어 기다리는 소비자에게는 이 틈이 남으며, 영속은 담는 쪽의 몫이다.

**기록은 줄지 않는다.** 소모된 열쇠마다 하나씩 늘고 지워지지 않는다. 열쇠 하나에 실행이 적어도 하나 서므로 실행 표(역시 지워지지 않는다)보다 커지지 않는다. §15.166 이 상한 없이 든다고 적은 목록에 이것이 하나 더해진다.

**다른 승인자의 id 와 값이 보인다.** 창구는 루프백 전용이고 신원을 인증하지 않는다(§15.3). 사건이 열린 실행이면 승인자는 사건 번들의 `approvedBy` 로 이미 나가지만, 사건이 열리지 않은 실행(아직 돌거나 문제없이 끝난 것)의 승인자와 값은 `CONSUMED` 로 처음 밖에 나간다. 그래도 싣기로 정했다 — 부르는 쪽이 «내 요청» 을 가르는 데 필요하고, 창구가 루프백에만 붙어 있다. 창구를 밖으로 내는 날 인증과 함께 다시 본다.

**소모의 판정이 자격보다 앞이다.** 지금 `NO_PROPOSAL` 이 자격 판정보다 앞인 것과 같은 자리다. 선언이 없는 부르는 쪽도 소모 기록을 본다.

**사람의 문은 산문으로 낸다.** 프로세스 안의 `approveRemedy` 는 소모된 제안에 다시 누르면 지금처럼 거절 사유 산문을 받는다. 그 산문이 승인자와 `executionId` 를 든다.

## 대는 것

v1 의 공개 경로로는 소모 뒤 같은 열쇠에 새 제안이 서지 않는다(위 «고르지 않은 것»). 그래서 아래 표의 `RemedyDeskTest` 행들은 장부(`RemedyDesk`) 수준에서 `record` · `judge` · `settle` 을 직접 불러 댄다. 짝 검사는 두 타입에 다 있고, 사람의 문은 `Judgment.No` 를 바로 산문으로 옮기므로 그 길에서는 판정 쪽 검사가 유일한 방벽이다 — 그래서 둘을 따로 댄다.

| 담보 | 시험 |
|---|---|
| 승인한 제안에 다시 시도하면 소모와 그 내용이 돌아온다 | `EntitlementTest` · `승인한 제안에 다시 시도하면 누가 언제 무엇을 보냈는지 돌려받는다` |
| 사람의 문으로 소모한 것도 기록되고, 밖의 문 재시도가 그것을 받는다 | `EntitlementTest` · `사람이 승인한 제안에 다시 시도하면 사람의 승인을 돌려받는다` |
| 사람의 문 재시도는 소모를 사유 산문으로 받는다 | `EntitlementTest` · `소모된 제안을 사람의 문으로 다시 누르면 소모를 사유로 받는다` |
| 소모 기록은 그 (기체, 주문)에만 묶인다 — 같은 기체의 다른 주문도, 다른 기체의 같은 주문도 소모가 아니다 | `EntitlementTest` · `다른 열쇠의 소모는 이 열쇠를 소모로 만들지 않는다` |
| 관문 거절 뒤의 재시도는 서 있는 제안으로 판정되고 제안이 남는다 | `EntitlementTest` · `관문이 거절해도 제안은 남는다` |
| 멱등 접힘 뒤의 재시도도 같다 | `EntitlementTest` · `멱등으로 접힌 승인은 소모가 아니고 제안이 남는다` |
| 소모 뒤 새 제안이 서면 새 제안이 이긴다 | `RemedyDeskTest` · `소모 뒤 같은 열쇠에 새 제안이 서면 새 제안이 이긴다` |
| 소모 뒤에도 가림이 맨 앞이다 | `RemedyDeskTest` · `소모 뒤 새 제안이 가려지면 가림이 먼저다` |
| 다시 소모되면 마지막 소모가 남는다 | `RemedyDeskTest` · `다시 소모되면 마지막 소모가 남는다` |
| 판정도 `CONSUMED` 와 기록이 짝으로만 선다 | `RemedyDeskTest` · `판정도 소모 거절만 소모 기록을 든다` |
| 거절 답의 `CONSUMED` 와 기록은 짝으로만 선다 | `ApprovalWireTest` · `소모 거절만 소모 기록을 든다` |
| 규약 판 "3" 과 `consumed` 칸의 모양 | `ApprovalWireTest` · `소모 거절이 누가 언제 무엇을 보냈는지 싣는다` |
| 다른 거절은 `consumed` 키를 null 로 싣고, 승인 답은 싣지 않는다 | `ApprovalWireTest` · `소모가 아닌 거절은 consumed 를 null 로 싣는다` |
| 창구가 `CONSUMED` 를 실제로 낸다 | `ApprovalHostTest` · `같은 제안에 두 번 승인하면 둘째는 소모로 거절된다` |

이 표는 게이트가 이름으로 대조하지 않는다. 이름은 시험과 손으로 맞춘다.
