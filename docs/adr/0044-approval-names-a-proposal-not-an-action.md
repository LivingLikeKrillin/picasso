# ADR 44 — 승인은 조치를 기술하지 않고 제안을 가리킨다

- **설계 문서 참조**: §6.4 (제안과 승인), §7 (자원 소유 대장), §15.172, ADR 9, ADR 42, ADR 43
- **결정 일자**: 2026-09-18
- **상태**: 결정됨 (코드베이스 반영 완료)

---

## 1. 맥락 및 배경

ADR 43 이 자동 승인 자격을 밖의 선언으로 확정했으나, 그 선언은 조치 유형(`skillTypes`)까지만 범위로 삼았습니다. 승인 API 는 걸음마다 파라미터를 호출자로부터 받았으며, 호출자가 프로세스 내부의 테스트뿐이었으므로 해당 구조의 문제가 드러나지 않았습니다.

프로세스 밖의 소비자가 승인을 시도하려는 시점에 두 가지 사실이 동시에 확인되었습니다.

- **선언이 범위를 덮지 못합니다.** `pick_place` 를 덮는 자격은 실질적으로 "임의의 대상을 임의의 위치에 놓을 수 있다" 이며, 선언이 기술한 범위와 실제 권한 사이에 간극이 존재합니다. 그 간극을 없애는 것이 자격이 존재하는 목적입니다
- **승인이 주문을 받습니다.** 승인 API 가 `JobOrder` 를 인자로 받으므로, 호출자는 임의의 주문을 구성하여 전달할 수 있습니다. 이는 승인 표면이 아니라 일반 접수 표면입니다

호출 가능한 값이 존재하지 않는다는 문제도 함께 확인되었습니다. 실측 결과 `profile/` 의 모든 스킬이 필수 파라미터를 요구하며, 대안 탐색의 걸음이 될 수 있는 스킬은 파지를 변경하는 것뿐이므로 전 카탈로그에서 `pick_place` 하나입니다. 해당 스킬은 `object_id` 와 `destination` 을 필수로 요구합니다. 탐색기는 그 값을 생성할 수 없다는 것이 기존 규율이므로, 자동 승인은 구조적으로 성립하지 않는 상태였습니다.

## 2. 핵심 결정 사항

**"승인은 조치를 기술하지 않는다. 이미 계산되어 거절된 제안 하나를 가리킬 뿐이며, 그 조치에 실릴 값은 사람의 선언과 기체의 관측에서만 온다."**

### 2.1 문을 둘로 나눕니다

| 문 | 호출 형태 | 값의 출처 | 선언 요구 |
|---|---|---|---|
| 사람의 문 (`approveRemedy`) | 제안의 열쇠와 값 | 승인 시점에 사람이 제공 | 요구하지 않음 (ADR 43) |
| 밖의 문 (`attemptApproval`) | 제안의 열쇠만 | 선언과 관측 | 요구함 |

- **밖의 문에는 값을 실을 칸이 없습니다.** 호출자의 권한이 "승인 시도 한 번" 을 넘지 않는 것은 규율이 아니라 표면의 형상에 기인합니다. 확대될 수 있는 칸이 존재하지 않습니다
- **주문은 제안과 함께 본 계층이 보관합니다.** 거절 시점에 계산된 주문을 제안 표가 함께 보유하므로, 승인자가 주문을 구성하여 전달할 경로가 없습니다
- **에이전트는 사람의 문으로 진입할 수 없습니다.** 값을 실을 수 있다는 것은 조치를 기술할 수 있다는 의미이며, 그 경우 실제 권한이 선언보다 넓어집니다
- **밖의 문은 승인자 종류를 구분하지 않습니다.** 값 없이 진입하는 경로에서는 선언이 곧 값의 출처이므로, 선언이 없으면 거절됩니다. 종류로 구분할 경우 사람 명의의 시도가 값 없이 통과하는 경로가 생성됩니다

### 2.2 값의 출처는 둘이며 계약이 이미 구분합니다

| 파라미터 | 출처 | 근거 |
|---|---|---|
| 계약이 `is_object_reference` 로 표기한 칸 | 관측 (`HoldState.objectRef`) | 무엇을 파지 중인지는 기체가 보고하는 사실이며, 사전 기재는 상황에 대한 사전 단정입니다 |
| 그 밖의 필수 칸 | 선언 (`DeclaredAction.parameters`) | 적재 위치는 현장의 상설 결정이며 상황에 따라 변동하지 않습니다 |

- **생성하는 경로는 존재하지 않습니다.** 어느 쪽도 충족하지 못하면 거절이며 사람에게 위임됩니다
- **선언은 좁히는 방향으로만 작동합니다.** 선언이 대상을 기재한 경우 관측과 일치해야 하며, 관측을 덮어쓰지 못합니다. 덮어쓰기가 허용되면 선언이 사실을 우선하게 되며, 자동 승인이 대상이 아닌 물체를 취급합니다
- **관측은 승인 시점에 다시 확인합니다.** 제안 수립 시점의 파지를 보관하면 그 사이에 기체가 적재물을 변경한 경우 낡은 사실로 승인이 성립합니다
- **걸음마다 효과로 전진시킵니다.** 첫 걸음이 적재물을 놓으면 다음 걸음이 파지할 대상의 명칭은 선언에도 관측에도 존재하지 않으므로 거절합니다 (§15.174)

### 2.3 거절은 값이며 오류가 아닙니다

- **거절 종류를 열거형으로 제공합니다.** 사유 산문만 제공하면 읽는 측이 문자열 대조에 의존하며, 그 검증은 거절의 발생만 확인하므로 모든 거절에 대해 통과합니다. 종류를 구분하는 기준은 후속 조치의 상이 여부입니다
- **거절은 정상 응답입니다.** 오류 코드로 전달하면 읽는 측에서 자격 부재와 시스템 장애가 동일한 형태가 됩니다. 오류로 전달하는 것은 해독 불가능한 요청뿐입니다
- **승인의 응답이 실제 전달된 값을 반환합니다.** 호출자가 값을 선택하지 않았으므로, 자기 명의로 전달된 내용을 확인하는 경로가 이것뿐입니다
- **관문 거절은 제안을 소모하지 않습니다.** 자리 경쟁이나 무소유 바닥으로 인한 거절은 자격의 문제가 아니며, 제안을 소모할 경우 조건 해소 후 사람이 승인할 대상까지 소멸합니다

### 2.4 전송은 포함하지 않습니다

`ApprovalWire` 는 문자열만 생성하고 해석하며 소켓과 파일을 인지하지 않습니다. `LedgerExport` 와 동일한 성질이며, 담는 측이 어떤 전송을 선택하더라도 본 규약은 유지됩니다. 본 계층이 라이브러리라는 성질(`docs/orchestration.md` §6)은 변경되지 않습니다.

## 3. 결정 근거

1. **선언이 범위가 되려면 값을 포함해야 합니다.** 조치 유형만 기재한 선언은 "적재물을 놓을 수 있다" 를 의도하지만 실제로는 "임의의 대상을 임의의 위치에 놓을 수 있다" 를 부여합니다. 원격 호출자가 등장하는 시점에 그 간극이 실제 권한 차이가 됩니다
2. **관측에서 값을 취하는 것은 생성이 아닙니다.** 어느 칸이 대상의 명칭인지는 계약의 `is_object_reference` 가 선언하며, 파지 중인 대상의 명칭은 `HoldState.objectRef` 가 보고합니다. 두 선언된 사실을 결합하는 것이며 추정이 아닙니다. 미믹은 동일한 사실을 역방향으로 사용합니다
3. **제안을 가리키는 형태가 권한을 형상으로 제한합니다.** 규율로 제한하면 규율이 준수되는 동안에만 유효하나, 칸이 존재하지 않으면 규율과 무관하게 성립합니다
4. **본 계층의 라이브러리 성질을 유지합니다.** 인코딩과 전송을 분리하므로 진입점도 HTTP 표면도 추가되지 않습니다

## 4. 검토된 대안

| 대안 | 기각 사유 |
|---|---|
| 파라미터를 요구하는 조치는 자동 승인 대상에서 제외 | 자격을 충족하는 조치가 0개가 되어 ADR 43 의 기구 전체가 도달 불가 상태가 됩니다. 결정성 기준 자체는 타당하나, 선언이 값을 포함하면 그 기준이 충족되므로 배제할 이유가 소멸합니다 |
| 파라미터가 불필요한 스킬을 신규 생성 | 실증을 목적으로 카탈로그에 스킬을 추가하는 것이며 소비자 존재 원칙(ADR 9)과 기존 어휘 기반 원칙(ADR 36)에 저촉됩니다. 실물 기체가 해당 스킬을 선언하는 시점에는 자연히 성립합니다 |
| 대상 명칭을 선언에서만 취득 | 파지 중인 대상은 사전에 확정할 수 없으므로, 선언이 상황을 사전 단정하게 됩니다. 관측과 불일치하는 경우 대상이 아닌 물체를 취급합니다 |
| 승인 시도에 자격 주장을 포함 | 호출하는 측이 자격을 스스로 판단하는 경로가 되며 ADR 43 의 판정 위치가 무효화됩니다 |
| 거절을 HTTP 오류로 전달 | 읽는 측에서 자격 부재와 시스템 장애가 동일한 형태가 되며, 거절이 설계된 정상 경로라는 사실이 소실됩니다 |
| 일반 미들웨어 API 를 공개 | 본 계층 외부의 권한은 조회와 승인 시도 둘뿐이며, 그 이상을 제공하면 규율이 아니라 자격증명 수준의 분리가 소멸합니다 |

## 5. 파급 효과

- **`Entitlement` 의 형상이 변경됩니다.** `skillTypes: Set<String>` 이 `actions: List<DeclaredAction>` 으로 대체되며, 조치 유형은 해당 목록에서 파생됩니다. 동일 유형의 중복 선언은 생성 시점에 거부합니다. 어느 값을 사용할지 선언이 답하지 않으며, 선택 규칙을 도입하면 그 규칙이 선언보다 우선하게 됩니다
- **승인 API 의 서명이 변경됩니다.** `JobOrder` 대신 `jobOrderId` 를 받습니다
- **신원은 여전히 위조 가능합니다.** 본 표면은 신원을 인증하지 않으며, 해당 값은 부인방지가 아니라 조사 단서입니다 (§15.3). 판정 자체는 본 계층 내부에서 수행되므로 호출하는 측이 위조할 수 없습니다
- **반복 카운터는 여전히 승인자 종류로 분리하지 않습니다** (ADR 43 §4). 본 결정은 값의 출처를 변경할 뿐 계량의 대상을 변경하지 않습니다
- **도달 불가 항목 둘이 대장에 등록되었습니다.** 파지 중이면서 명칭을 보고하지 않는 관측(§15.173)과 둘째 걸음의 대상 명칭(§15.174)이며, 전자는 순수 판정 함수의 단위 시험에서만 재현됩니다
