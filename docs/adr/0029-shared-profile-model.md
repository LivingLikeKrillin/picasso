# ADR 29 — `profile-model`을 뽑아 `gate`와 `mimic`이 공유한다

설계 §14에 없던 결정이다. 2단계 Chunk 1에서 내렸고 §3.1·§3.2의 그래프를 바꾸므로 기록이 필요하다.

## 맥락

프로파일 문서를 읽는 코드가 `gate`와 `mimic` 양쪽에 필요하다.

- `gate`는 검사 3·4·6에서 문서를 읽어 스키마·계약·기준선과 대조한다.
- `mimic`은 문서를 읽어 `Capability`로 투영하고 거동을 파생한다(§10.1).

`mimic`이 `gate`에 의존할 수는 없다 — 게이트는 buf 실행기와 검사 아홉을 끌고 오고, §3.2의 그래프에도 그런 간선이 없다.

## 결정

**새 모듈 `profile-model`을 만들어 둘이 공유한다.**

```
profile-model → (없음)
gate          → profile-model
mimic         → profile-model, contracts
```

`profile-model`은 `contracts`도 모른다. 프로파일은 계약을 **참조만** 하고 확장할 수 없으므로(§7.3), 문서 모델이 계약 타입을 쓸 일이 없다. `contracts`의 프로젝트 내 의존은 여전히 0이라 게이트 검사 5번이 그대로 통과한다.

## 반대 논거와 그것을 택하지 않은 이유

**두 벌로 두면 완료 기준 10의 투영 일치 시험이 서로 다른 두 구현을 대조하게 되어 더 강하다**는 주장이 가능하다. 실제로 독립 구현 둘이 서로를 검증하는 것은 좋은 성질이다.

택하지 않았다. §12.2의 10번이 잡겠다는 것은 **"능력을 하드코딩하는 것"**이지 "JSON을 잘못 읽는 것"이 아니다. 후자는 스키마 자체와 게이트 검사 3번이 잡는다. 그리고 손으로 쓴 파서 두 벌의 드리프트는 안전망이 아니라 **버그 원천**이다 — 이 프로젝트가 존재하는 이유가 정확히 그 드리프트를 막는 것인데, 우리 코드가 그것을 내면 곤란하다.

## 부수 이득 하나

`ProfileDocument.NON_PROJECTION`은 §7.2가 정한 비투영 집합이다. 게이트 6번(어휘 diff에서 뺀다)과 `mimic`의 투영(싣지 않는다)이 **같은 상수를 써야 옳다.** 두 벌이면 한쪽만 고쳐 어긋날 수 있고, 그 어긋남은 "게이트는 통과했는데 투영이 비투영 값을 실었다"로 나타난다.

## 대가 — 모듈 경계가 공짜가 아니었다

추출이 "기능 변경 0"일 줄 알았는데 셋이 깨졌다. **전부 컴파일 오류라 조용히 지나가지는 않았지만, 미리 알지 못했으면 원인을 찾는 데 시간을 썼을 것들이다.**

1. **Kotlin 스마트 캐스트가 모듈 경계에서 죽는다.** 다른 모듈의 nullable `val`은 공개 API 프로퍼티라 값이 바뀔 수 있다고 컴파일러가 본다. `Check06Vocabulary.narrowing()`에서 6건이 터졌다. 지역 변수로 받아 고쳤다.
2. **같은 패키지라 import 없이 쓰던 것이 드러난다.** `GateInputTest`가 `ProfileKey`를 import 없이 썼고, FQN 기반 치환은 그것을 못 고친다.
3. **새 모듈에 `kotlin("test")`가 필요하다.** 루트가 junit-jupiter만 넣는다.

그리고 시험 입력 선언이 함정이었다. `profile/fixtures`를 `gate`에서 **옮기면** 안 되고 `profile-model`에 **더해야** 한다 — 게이트 음성 케이스 넷이 그 픽스처를 overlay하고 음성 하네스가 원본을 직접 읽으므로, 빼면 픽스처를 고쳐도 시험이 `UP-TO-DATE`로 넘어가는 구멍이 다시 열린다.
