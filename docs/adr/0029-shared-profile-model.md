# ADR 29 — 기종 프로파일 공용 파싱 모델(`profile-model`) 분리 및 공유

- **설계 문서 참조**: §3.1, §3.2 (모듈 의존성 그래프)
- **결정 일자**: 2026-09-08
- **상태**: 결정됨 (코드베이스 반영 완료)

---

## 1. 맥락 및 배경

기종 능력 프로파일(JSON) 문서를 역직렬화하는 로직이 정적 검증기(`gate`)와 가상 런타임 에뮬레이터(`mimic`) 양쪽 모두에서 필수적으로 요구되었습니다:
- `gate`: 스키마 정합성 검사(검사 3), 계약 교차 참조(검사 4), 개정판 변경 검증(검사 6)에서 프로파일 파싱 필요
- `mimic`: 프로파일을 읽어 `Capability` 모델로 투영하고 가상 거동을 파생하기 위해 파싱 필요 (§10.1)

그러나 아키텍처 원칙상 `mimic`이 `gate`에 의존할 수는 없으며(불필요한 빌드 검증 도구 결합), 반대로 `gate`가 `mimic`에 의존할 수도 없습니다.

---

## 2. 핵심 결정 사항

**"프로파일 문서를 역직렬화하는 경량 도메인 모델 모듈인 `profile-model`을 독립 신설하여 `gate`와 `mimic`이 공통 의존하도록 구성한다."**

```
profile-model → (내부 의존성 없음)
gate          → profile-model
mimic         → profile-model, contracts
```

`profile-model`은 `contracts` 모듈도 참조하지 않으며 순수한 JSON 데이터 매핑만을 전담합니다. 이를 통해 `contracts`의 프로젝트 내부 의존성 0 원칙(검사 5번)을 완벽히 유지합니다.

---

## 3. 독립 분리 채택의 기술적 근거

에뮬레이터와 검증기가 각자 독립적인 파서를 구현하여 상호 검증하는 방안도 검토되었으나, 다음 이유로 기각되었습니다:
1. 완료 기준 제10조가 검증하고자 하는 핵심은 **"기체의 능력을 하드코딩하지 않고 프로파일로부터 올바르게 동적 파생하는가"**이지, JSON 파서 자체의 동작 여부가 아닙니다.
2. 수동으로 작성된 2개의 독립 파서는 필연적으로 파싱 규칙 드리프트를 유발하며, 시스템의 일관성을 해치는 주된 원인이 됩니다.
3. `ProfileDocument.NON_PROJECTION`과 같은 비투영 상수 정의를 양쪽 모듈이 단일 소스로부터 공유함으로써 투영 불일치를 원천 방지할 수 있습니다.
