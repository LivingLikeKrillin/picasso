# adapter-host — 공용 어댑터 호스팅 런타임 서버 (Adapter Host Server)

기종별 구현체(`RobotAdapter`)를 주입받아 표준 인터페이스 계약(제4계층)의 gRPC 서비스를 노출하는 **기종 중립 계약 서버**(ADR 39)입니다. 4개 기종별 어댑터가 개별 서버를 구축하지 않고 본 공용 호스트를 공유합니다.

어댑터 계층 전체 아키텍처는 `adapter-core`(노스바운드 표준 어휘) · `adapter-host`(공용 계약 서버) · `adapter-<기종>`(벤더 연동 전담, ADR 33)의 3계층으로 분리되어 있습니다.

---

## 1. 아키텍처 설계 원칙: 단일 서버 인프라를 통한 동작 일관성

상위 클라이언트(`client`, `picasso`)는 기종을 일체 인지하지 않으므로, 인터페이스 계약 뒤의 구현체(에뮬레이터 및 실제 하드웨어 어댑터) 간 동작 차이가 없어야 합니다. 서버 런타임을 단일화함으로써 통신 처리 로직의 불일치 위험을 최소화합니다.

또한 `capability`(케이퍼빌리티 프로젝션 및 협상 판정)와 `uplink`(원격 상태 발행 및 적재) 공용 라이브러리를 공유하여, `harness/HostParityTest`를 통해 에뮬레이터와 실제 하드웨어 어댑터 간의 완전한 동작 동치성을 유지합니다.

---

## 2. 어댑터 계층 3단계 분리 구조

| 계층 | 인지 영역 (Responsibility) | 격리된 영역 (Encapsulation) |
|---|---|---|
| `adapter-core` | 계약 도메인 어휘 (`Acceptance`, `Applied`, `HoldObservation`, `ProgressObservation`, `SiteNames`) | 기종 고유 사양, 네트워크 전송 계층 |
| `adapter-host` | 인터페이스 계약 gRPC 엔드포인트, 태스크 이력 관리, 3대 비동기 스트림 발행, 케이퍼빌리티 협상 | 기종 고유 사양, 벤더 API 프로토콜 |
| `adapter-<기종>` | **벤더 고유 연동 전담** — 사우스바운드 통신 포트, 벤더 심볼 인용(`@VendorSurface`), 기체 조립 | 상위 계약 소비자의 정체 |

---

## 3. 결정론적 펌프(Pump) 구동 및 비동기 스레드 배제

인입 RPC는 기본적으로 내부 상태 갱신 틱인 `pump`를 선행 통과합니다. 호스트는 어댑터에 기체 상태를 질의하고 변경된 전이만을 기록하여, `WatchTask` 스트림이 타 RPC에 의한 중간 전이를 놓치는 레이스 컨디션을 방지합니다. 펌프는 호스트 잠금 아래에서 도는 태스크와 로그 길이를 정하는 `plan`, 링크 잠금만 쥐고 어댑터 상태와 실패·결과·진행률·파지·결함을 묻되 기록을 만지지 않는 `read`, 호스트 잠금 아래에서 적는 `apply`의 세 단계로 나뉘며 잠금 순서는 언제나 호스트 다음 링크입니다. 새 선택인 `AdapterHost.pumpOnRead`가 거짓이면 링크를 안 쓰는 읽기 RPC는 펌프를 건너뛰고 마지막 기록값으로 답하며, 명령과 `GetKnownSiteNames`는 끝난 태스크를 읽지 않은 채 새 접수를 거절하지 않도록 언제나 펌프를 먼저 지납니다(참이면 모든 RPC가 펌프를 통과합니다). 이에 따라 외부 배치는 `HostedRobot.pump`를 직접 부르지 않고 반드시 `AdapterHost.pump`를 호출하여 호스트 잠금을 거쳐야 합니다. 동시 유입된 태스크 시작 요청이 단일하게 수락되어 중복 처리가 거부되는지는 `AdapterHostConcurrencyTest`가 검증하며, 사우스바운드 읽기 중 읽기 RPC 응답성과 경합 시의 상태 전이 버림 및 결함 표 보존, 그리고 기본 구현을 포함한 어댑터 호출의 링크 잠금 직렬화는 `HostLinkReadTest`가 검증합니다.

명령 RPC와 `GetKnownSiteNames`는 본문을 호스트 잠금 아래로 줄 세우지 않고 잠금 밖에서 실행합니다. 접수는 호스트 잠금 아래에서 기체별 보낼 자리(`sending`)를 잡고 링크 잠금만 쥔 채 어댑터 송신과 관측 조회를 수행한 뒤 다시 호스트 잠금 아래에서 기록하고 자리를 비우는 3단계로 동작합니다. 송신 중에 동일 요청이 오면 합류하여 결과를 기다리고 다른 접수는 즉시 거부하며, 조작은 거부 없이 진행 중인 명령이 끝날 때까지 대기합니다. 펌프는 확정 전 상태 역전을 막기 위해 송신 중인 명령이 있으면 태스크 전이를 적지 않고 건너뜁니다. 이러한 분리 구조와 응답성은 `HostCommandSendTest`를 통해 검증합니다.

상태 발행과 연결 보고가 싣는 생존 보고의 내용(`LivenessFacts`) 또한 발행 자리에서 어댑터에 묻지 않고, 상태 발행 차례에 펌프의 `read` 단계가 링크 잠금 아래에서 미리 읽어 둔 값을 씁니다. 기동 때에는 포트를 열기 전에 호스트 잠금 밖에서 한 번 읽어 두어(`primeLiveness`) 첫 연결 보고부터 값을 채우며, 발행 차례가 아닌 펌프 주기에는 다시 묻지 않습니다. 상태 발행 차례의 사이트 이름 조회가 지연되는 동안에도 스냅숏이 기다리지 않는다는 점과 기동 및 발행 차례에만 읽는다는 점은 `HostLivenessReadTest`가 검증합니다.

어댑터가 접수를 `LINK_IN_DOUBT`로 거부하면 호스트는 사우스바운드 호출이 나갔는지 모르는 상태로 다루어 장부에 올리지 않고 `inDoubt`에 기록하며 gRPC `UNKNOWN`으로 답합니다. 이후 같은 `task_id`와 `revision`의 접수가 다시 들어와도 어댑터로 다시 보내지 않고 기록해 둔 같은 답을 돌려줍니다. 이 동작과 `LINK_ERROR`일 때 다시 보내는 동작의 차이는 `HostInDoubtSendTest`가 검증합니다.

## 4. 알려진 한계 및 엔지니어링 고려 사항

- **실제 하드웨어 기체 연동 미수행 (C-3)**: 어댑터 4종 중 어느 것도 실제 하드웨어에 연동 검증되지 않았으며, 네트워크 회선을 통과하는 Orbit 역시 테스트용 스텁 서버와 연동된 상태입니다 (상세 등급: [`docs/verification.md`](../docs/verification.md) 5·6번).
- **단일 프로세스 다중 기체 호스팅 (ADR 21)**: 현재 구현은 PoC 개발 편의를 위해 단일 호스트 프로세스에서 복수 기체를 수용하도록 구성되어 있습니다.
- **재개/재시도 미지원 (§15.113)**: 포트 인터페이스 사양은 확장되었으나 기종별 어댑터의 기본값은 아직 미지원 상태입니다.
