# registry — 운영 원장 및 구성 관리 서비스 (Operational Registry)

인터페이스 계약이 아닌 **시스템 운영 상태와 생명주기를 관장하는 서비스**입니다. 기종 프로파일 개정판 관리, 어댑터 인스턴스 생명주기 추적, 런타임 바인딩, 의존성 원장, 무중단 변경 계획, 사이트 카탈로그 및 진단 표면을 담당합니다. 기술 스택은 Spring Boot와 PostgreSQL 16 기반으로 구현되어 있습니다.

---

## 1. 아키텍처 설계 원칙: 풀(Pull) 기반 통신 및 비동기 적재

- **클라이언트 직접 푸시 금지 (§3.2)**: 레지스트리는 런타임 클라이언트나 에뮬레이터로 직접 설정을 푸시하지 않습니다. 갱신된 프로파일은 `mimic` 등이 제어 채널 요청에 따라 **풀(Pull)** 방식으로 조회하며, 상태 관측값은 지정된 적재 엔드포인트로 인입됩니다.
- **주기적 배경 폴링 배제**: 에뮬레이터 프로세스 내에 자체 주기 스레드를 두지 않고 상위 제어 채널 트리거에 의해 동기화를 수행합니다 (5초 폴링 간격 운영 설정, §15.5). 레지스트리 장애가 로봇 기체의 실시간 제어 루프를 즉시 중단시키지 않도록 설계된 결합도 격리 대가입니다.

## 2. 모듈 패키지 구조

| 패키지 | 기능 및 역할 |
|---|---|
| `revision/` | 프로파일 개정판 생명주기 관리(`DRAFT` → `ACTIVE` → `SUPERSEDED`), 게이트 규칙 재검증, 스킬 타입 동기화, 폐기 예고 |
| `adapter/` | 어댑터 제품 모델, 빌드 사양(`adapter_version`), **배포된 런타임 인스턴스**(`adapter_instance`) 추적 (3대 축) |
| `binding/` | 기체-어댑터-개정판 바인딩. **기체 등록 2대 경로**(운영자 선언 및 런타임 자동 발견, ADR 37), 사이트 명칭 매핑 |
| `ledger/` | 의존성 원장 관리 — 기능별 활성 소비자 추적. 30일 이상 미갱신 시 비활성 상태 전환 (이력 보존) |
| `plan/` | 무중단 변경 계획 및 단계별 전제 조건 검증. **활성 소비자가 0에 도달하기 전 기능 축소 계획은 자동 거부** |
| `catalog/` · `diag/` | 사이트 공간 카탈로그 제공 및 10개 진단 REST 표면 노출 |
| `ingest/` · `observe/` | 상태 적재 파이프라인 — 핸드셰이크, 하트비트 생존 확인, 태스크 진행률 및 신규 기체 발견 이벤트 수신 |
| `web/` | REST API 계층. **이원화된 토큰 체계** — 기체용 적재 토큰(`/ingest/*`) 및 운영자용 관리 토큰(`/operations/*`) 분리 |

데이터베이스 스키마는 Flyway 마이그레이션 스크립트를 정본으로 유지합니다 (`src/main/resources/db/migration/`, V1~V15).

## 3. 접근 제어 이원화 설계 (Dual Gateway Architecture)

- **적재 토큰과 운영자 토큰의 엄격한 분리 (§15.38)**: 기체별로 분배되는 상태 보고용 적재 토큰이 탈취되더라도, 시스템 바인딩이나 구성 계획을 변경하는 운영자 권한으로 승격되는 보안 사고를 원천 방지합니다.
- **인입 경로 기반의 기체 등록 출처 판별 (ADR 37)**: 기체의 신원 등록은 페이로드의 자체 선언 필드가 아닌 **인입된 HTTP 엔드포인트**를 통해 출처를 엄밀히 판정합니다. `/ingest/*`를 통해 들어오면 '동적 발견(Discovered)', `/operations/*`를 통해 등록되면 '사전 선언(Declared)'으로 판정하여 발신자의 스푸핑을 방지합니다.

## 4. 자동화 테스트 및 검증 환경

- **실제 PostgreSQL 16 연동 (Testcontainers)**: 임베디드 H2 대신 실제 PostgreSQL 컨테이너 환경에서 실행되어 테이블 제약 조건, CHECK 제약, 외래키(FK) 무결성을 엄밀히 검증합니다.
- **실제 HTTP 엔드포인트 통합 테스트**: `TestRestTemplate`과 임의 포트 바인딩을 통해 HTTP 응답 상태 코드, 이원화 토큰 인증 및 JSON 직렬화를 실제 통신 환경에서 검증합니다.
- `web/*EndpointTest` 넷이 전체 REST 표면 계약을 검증하고, `binding/`, `plan/`, `ledger/` 단위 테스트가 비즈니스 규칙을 담당합니다.
- 상위 통합 검증은 `harness` 모듈에서 담당합니다: `LedgerIngestEndToEndTest` (에뮬레이터 경로), `HostIngestEndToEndTest` (어댑터 경로), `OrbitDiscoveryEndToEndTest` (동적 발견 경로).

## 5. 알려진 한계 및 엔지니어링 고려 사항

- **엔터프라이즈 인증 시스템 미통합 (§15.38)**: 현재는 역할 기반 이원화 토큰 체계만 구비되어 있으며, 안전한 운영을 위해 네트워크 경계 수준의 방화벽 격리를 전제합니다.
- **원장 적재의 비동기 메시지 브로커 구독기 미구현 (§15.34)**: 상태 발행은 외부 MQTT 브로커로 전달되나, 브로커로부터 이벤트를 읽어 원장에 자동 반영하는 컨슈머가 아직 구현되지 않아 현재는 프로세스 내 직접 적재 방식을 병행합니다.
- **원장 정합성의 계약 인터페이스 경유 의존성 (§15.10)**: 모든 클라이언트가 본 인터페이스 계약을 통과할 때만 원장의 완전성이 보증됩니다.
